# 知识库维护说明

## 基本原则

1. 已发布菜谱默认不可原地覆盖。需要改内容时新增更高版本，例如 `v2.md`。只有错字、用量微调、补角色标注这类小改，可以用 `npm run recipe -- revise <recipe_id> <version> <source.md> --minor-edit` 原地修订（只对当前生效版本有效，不升版本；旧版本和归档版本仍然不可变）。拿不准算不算"小改"就走升版本。
2. Obsidian 文件名和双向链接服务于人；`recipe_id`、`ingredient_id`、版本和状态服务于 MCP。
3. 食材替换（`substitutions/`）现在只用于真正"换成另一种食材"的规则，必须说明适用菜谱/角色、步骤变化、过敏原变化和依据。单纯"能不能省略"不再单独建文件，直接写在菜谱自己的 `ingredients[].optional` + `notes` 里。
4. 菜谱之间"能不能互相替代"不再靠人工建关系，靠每篇菜谱自己的 `dish_role` 标签实时匹配（见下）。`dish_role` 匹配出的候选只表示"类型上可以互相替代"，不表示价格一定更低——预算换菜必须重新汇总采购并报价。
5. 新内容先设为 `draft`；经过结构校验和人工审核后再改为 `published`。
6. 正文必须包含三个非空章节：`## 做法`、`## 替换建议`、`## 储存与安全`，缺一个都会在 `validate` 时报错。

## 食材的角色标注（V0.5）

`ingredients[]` 每项可以选填三个字段，`role`/`optional`/`defines_dish`（复用 `substitutions/` 已有的角色枚举）。不确定就不填，不要瞎猜——缺失时系统会保守跳过，不会当成默认值处理：

- `role`：`primary`（主料）| `supporting`（配料）| `seasoning`（调味）| `garnish`（点缀）| `cooking_medium`（油/介质）。购物清单按份数缩放时，`seasoning`/`garnish`/`cooking_medium` 是打折缩放，不是严格跟人数等比例。
- `optional`：这个食材能不能整体不放。
- `defines_dish`：换掉/去掉这个食材，还算不算同一道菜。`true` 的食材缺货时，`find_replacements` 只会给"换成别的菜"的候选（按 `dish_role` 实时检索出来的整菜候选），不会假装成"稍微调整一下"。

现在全部菜谱都已经标注了这三个字段。这是判断题，不是格式题——起草你的判断，但要让用户确认过之后再发布。

## 菜品角色标注（`dish_role`）

菜谱顶层可以选填这一个字段，标这道菜在一餐里通常是什么角色，用于配餐和整菜替代的实时检索：`protein`（荤/主菜）| `vegetable`（素菜/配菜）| `soup`（汤）| `staple`（主食）| `cold_dish`（凉菜）| `mixed`（荤素难分，如蛋类/豆腐类主料但没肉或肉只是配料）| `other`（确实不属于以上任何一类）。不确定就先不填，缺失时系统会提示未按分类过滤，不会报错。荤素界限不清楚的菜优先考虑 `mixed`。

`mixed`/`other` 样本少，同分类候选池小，查询时可能出现"候选被过滤到剩 0 个"的情况——这是分类样本少的真实局限，不是 bug。

## 新建菜谱

1. 在 Obsidian 里新建笔记，`Ctrl/Cmd+P → Insert template` 插入 `templates/recipe-template.md`。
2. 按模板填写 frontmatter 和三段正文，`status` 先保持 `draft`。
3. `npm run recipe -- validate` 确认 schema、三段式正文和引用都通过。
4. `npm run recipe -- create-draft <文件路径>` 把内容规范化进 `drafts/` 并确定版本号。
5. `npm run recipe -- publish <recipe_id> <version>` 发布为不可变版本（会自动跑过敏原复核）。

## 新增内容后的检查

- `npm run recipe -- validate`
- `npm test`
- 确认 Obsidian 中的双向链接没有指向错误版本。

## 换菜/配餐怎么处理

- 食材买不到、想省略：直接在菜谱自己的 `ingredients[].optional` + `notes` 里说明，不用建文件。
- 食材买不到、想换成别的食材：在 `substitutions/` 建一条 `mode: replace` 规则，写清适用菜谱/角色、步骤变化、过敏原变化。
- 想整道菜换成另一道：不用手动建关系，给两道菜都打好 `dish_role`，`find_replacements` 会自动按同分类检索出候选。
- 想凑一餐（几荤几素）：同样靠 `dish_role`，不需要手动声明"这两道菜适合搭配"；所有入选菜仍要进入采购汇总和校验。
- 有些搭配/替代关系里有具体的过敏原或用时提醒值得保留（不是靠 `dish_role` 能自动推出来的），直接写进对应菜谱的"替换建议"正文，当作人读的提示，不需要建结构化文件。
