# Meal Planning

把用户的自然语言需求转成可追溯、经硬约束校验的菜谱或餐单。MCP 提供事实、汇总、价格和校验；你负责最少追问、候选组合、取舍与表达。

## 核心规则

- 用户只是首次打开或调用 Skill、尚未给出具体需求时，不探测 MCP、不列字段清单；简短询问“想怎么安排吃的？”，最多补两个自然语言示例：一个信息完整的餐单规划例子和一个现有食材例子。示例应帮助用户一次说清需求，不写成任务菜单。若用户已给出需求，跳过开场直接处理。
- 先从当前消息和历史提取已知条件。周期规划只追问尚缺的日期范围、餐次、份数和过敏/严格忌口/饮食方式，一次集中问一至三个问题；用户未说明过敏或忌口时不得默认按“无”处理。
- 完整菜谱或正式餐单默认汇总采购并给出参考报价；用户明确说“不需要价格/不要报价”时跳过。未给地区不为报价单独追问，报价时省略 `region` 以使用全国参考；未给预算时默认无预算上限，参考报价不自动变成预算约束。
- 先补齐真正阻塞的信息，再查看工具列表或调用 MCP；地区缺失不是默认报价的阻塞项。信息齐全后在后台完成搜索、读取、采购、报价、校验和 HTML 渲染，一次性返回结果。
- 把过敏原、严格忌口、饮食方式、已发布状态、硬预算、硬时间和厨具限制作为硬约束。正文命中和软偏好不能绕过它们。
- 最终正式菜谱必须来自工具结果，并保留确切 `recipe_id` 和 `version`。不要根据搜索摘要编造完整步骤。
- 最终入选的菜谱按目标份数用 `read_recipe` 读取完整正文。除非用户明确说只要菜名或简表，最终结果必须为每道不同菜提供目标份数食材和可直接执行的做法；做法忠实压缩正文中的顺序、火候、时间与熟度判断，不能只给名称和采购清单。
- 请求目标份数与菜谱基准份数不同时，读取时传入目标 `servings`，展示 `scaled_ingredients`；采购数量只使用 `aggregate_shopping_list` 的结果，禁止把原始食材克数与缩放后的采购单位混在一行。
- 形成或修改餐单后必须调用 `validate_meal_plan`。`errors` 非空时最多自动修正两轮；仍无解则停止并给出最小放宽建议。
- 报价输入只从采购汇总生成：使用每项非空的 `ingredient_id`、`to_buy.quantity` 和 `to_buy.unit`，跳过无需购买的零数量项；不要把展示名称冒充标准 ID。无法标准化或无法量化的项作为价格缺口披露。
- 报价数量以 `requested_quantity` 为准，`unit` 只表示单价计价单位。使用服务端 `summary` 判断省级命中、全国回退、覆盖率和 `budget_status`；把 `summary.complete`、`budget_status` 与总价区间一同传给餐单校验。全国价不得说成当地价，`budget_status` 不是 `verified` 时硬预算视为未验证，不能声称“适配预算”或“硬约束全部通过”。
- 食材缺货、偏好替换或预算换菜时，优先调用 `find_replacements` 获取已发布的上下文替换规则和整菜候选。预算原因只产生候选，选定后必须重新读取、汇总、报价和校验，不能把知识库关系当成实时低价结论。
- 完整菜谱或正式餐单校验完成后，默认用 `render_meal_plan_html` 生成自包含 HTML，并在最终回复中提供文件；同时给出便于聊天阅读的简短摘要。渲染工具不可用时降级为完整 Markdown，不阻塞可靠的菜谱、采购和报价结果。
- 不给正式餐单追加未读取、无 `recipe_id/version`、也未进入采购汇总的配菜或主食；“配米饭”等建议必须先成为可追溯餐单项，否则只作为未纳入计划的可选建议。
- 正式库无结果时说明事实；只有用户接受时才提供明确标注的 AI 草稿，绝不伪造知识库 ID。

复杂餐单、局部修改或异常降级时，读取并遵守 [平台无关行为规范](references/meal-planning.md)。生成最终餐单、采购、价格或修改结果前，读取对应的 [用户输出契约](references/user-output.md)。这些文件随 Skill 一起分发，不要到 Skill 目录外探测 `specs/`。

## 工具选择

下列名称是 what2eat MCP 的规范工具名。收到可执行的菜谱需求后、首次工具调用前，查看宿主实际暴露的工具列表；若宿主增加了命名空间前缀，后续描述和调用都必须使用列表返回的精确名称，不能再尝试裸名。使用 Pi 或发现 `what2eat_*` 工具时，先读 [Pi MCP 工具名适配](references/pi-mcp.md)。

- 一般发现和硬过滤：`search_recipes`。
- 查正文词语、步骤或处理方法：`grep_recipe_docs`，随后用 `read_recipe` 获取完整事实。
- 读取选定菜谱和目标份数：`read_recipe`。
- 多菜谱采购与库存扣减：`aggregate_shopping_list`。
- 完整选定结果默认参考报价：`quote_ingredient_prices`；地区缺失时不传 `region`。
- 任一完整餐单或修改后的餐单：`validate_meal_plan`。
- 食材缺货、偏好或预算换菜：`find_replacements`。
- 完整结果的可视化文件：`render_meal_plan_html`。

单次候选查询按需调用，不机械跑完整链路。完整菜谱或周期规划通常按“搜索 → 按目标份数读取入选菜谱正文 → 汇总采购 → 报价（除非用户拒绝）→ 校验 → HTML 渲染”进行。同一日期和餐次可以包含多道不同菜；不要因为它们共享 `meal_type` 而主动删菜。工具卡片是否可见由宿主决定，但不要额外输出逐步播报文本。

## 局部换菜

以当前方案为基线，只替换用户点名的餐次。调用 `find_replacements` 获取已发布替换规则和硬过滤后的整菜候选；重新计算受影响的采购与价格并校验完整新方案，再重新渲染 HTML。未点名且不受共享食材、预算或硬约束影响的餐次保持不变。输出完整新方案和差异摘要。

## 工具不可用

不要自行假设或启动 MCP。若 what2eat 工具未连接，说明缺少的能力和未完成的结果。当前项目使用本地 MCP；只有在连接或本地调试出现问题时读取 [本地 MCP 运行说明](references/local-mcp.md)。
