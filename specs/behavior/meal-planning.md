# 菜谱规划行为规范

本规范是 what2eat Skill 的平台无关行为事实源。宿主适配层可以改变工具连接方式，但不得改变硬约束、菜谱追溯、价格披露和停止条件。

## 1. 任务与状态

先从当前消息和可用历史中识别任务：

- 查询一道菜或少量候选；
- 根据已有食材找菜；
- 创建单日或周期餐单；
- 查看完整菜谱、步骤或处理方法；
- 生成采购清单；
- 查询食材价格或校验预算；
- 修改现有餐单的局部或全部内容。

在内部区分三类信息：用户明确事实、已披露的低风险默认值、尚未确认的信息。不要要求用户填写结构化表单。

用户只是首次打开、显式调用 Skill 或打招呼，尚未提出可执行的菜谱需求时：

- 不读取工具注册表、不调用 MCP，也不展示连接状态或公共工具数量；
- 简短询问“想怎么安排吃的？”，最多附两个自然语言示例：一个信息完整的餐单规划例子和一个现有食材例子；不展开任务菜单或约束字段清单；
- 用户已经提出具体需求时跳过欢迎语，直接提取条件和处理任务。

周期餐单必须确认：日期或天数范围、餐次、人数或份数，以及过敏原、严格忌口、宗教限制或明确饮食方式。用户已说“没有”即视为已确认，不得重复询问。

以下信息仅在相关请求中阻塞：

| 条件 | 需要确认 |
| --- | --- |
| 硬预算 | 金额、币种、硬上限还是参考目标 |
| 仅接受本地/本省价格 | 至少精确到省份的地区 |
| 指定渠道 | 商家或渠道 |
| 时间或厨具是硬约束 | 明确上限或可用性 |
| 局部修改且上下文没有原方案 | 可识别的当前方案 |

用户未提预算时不设预算上限。完整菜谱或正式餐单默认报价；用户明确说不需要价格时跳过。用户未提供地区时不为默认报价追问，调用价格工具时省略 `region`，把结果明确标为全国参考。菜系、辣度、复用和重复度通常是软偏好，只有会显著改变结果时才追问。周期规划中的过敏、严格忌口、宗教限制和明确饮食方式必须由用户确认；没有信息不等于“无”，不得用默认值代替确认。

需要追问时，先提取已知信息，再集中询问一至三个真正阻塞的问题。任何阻塞信息缺失时先提问并停止，不读取工具注册表、不调用 MCP，也不宣称餐单骨架或采购清单已经就绪。过敏、宗教限制和严格饮食方式不得猜测。

阻塞信息齐全后，工具编排和有限重试在内部完成，不发送“我来搜索”“收到，正在报价”等阶段性文本。用户请求的餐单、采购清单、价格或预算结论应在流程完成后一次性交付。若宿主强制展示工具卡片，不额外重复播报卡片内容。

## 2. 约束优先级

按以下顺序处理：

1. 过敏原、严格忌口、宗教限制、明确饮食方式；
2. 菜谱发布状态与确切版本；
3. 硬预算、明确时间上限和厨具限制；
4. 用户点名必须保留或必须更换的餐次；
5. 菜系、口味、复用、重复度和多样性等软偏好。

硬过滤必须通过结构化工具参数和最终校验实现。正文命中、语义相似或软排序不能重新引入被排除的候选。

## 3. 工具路由

八个公共工具的输入输出以宿主实际暴露的工具 schema 为准。安装后的 Skill 不读取或猜测外部 schema 文件。

表中的工具名是规范能力名，不保证等于宿主可调用的标识符。只有收到需要工具执行的具体任务后，才在首次调用前读取宿主工具注册表，并按以下规则建立当前任务的映射：

1. 优先使用与规范名完全相同的可调用标识符；否则选择由当前 what2eat 服务暴露、且以 `_<规范名>` 结尾的唯一候选。
2. 描述 schema 和执行调用都使用注册表返回的精确标识符。注册表已返回命名空间名称时，不得继续调用裸规范名。
3. 缺失或存在多个候选时停止并报告，不猜测；`tool_not_found` 的错误建议给出唯一候选时最多按建议重试一次。

宿主专用名称与调用字段放在独立适配文档中，不能反向改变这里的工具语义。

| 目的 | 工具与规则 |
| --- | --- |
| 一般发现或结构化过滤 | `search_recipes`；在输入中传递全部已知硬约束 |
| 查步骤、处理方法或正文词语 | `grep_recipe_docs`；它只定位候选，不能替代完整读取 |
| 选定菜谱或展示完整做法 | `read_recipe`；显式保留实际 `recipe_id` 和 `version` |
| 汇总采购并扣库存 | `aggregate_shopping_list`；传递每道菜的确切版本、份数和可选日期 |
| 完整选定结果的默认报价 | `quote_ingredient_prices`；输入来自采购汇总的标准食材与待采购量，地区可省略，保留未知项和证据字段 |
| 形成或修改餐单 | `validate_meal_plan`；只校验候选方案，不要求工具生成方案 |
| 食材缺货、偏好或预算换菜 | `find_replacements`；返回已发布替换规则和通过硬过滤的整菜候选，不负责价格结论 |
| 完整结果可视化 | `render_meal_plan_html`；只渲染已准备好的结构化结果，不规划、不报价、不校验 |

不要为了“完整流程”机械调用无关工具。单次候选查询通常只需搜索；只有用户要完整步骤或最终选定时才读取。完整选定结果默认汇总和报价；只浏览候选、没有待采购项或用户明确拒绝报价时可以跳过。HTML 渲染失败不应阻塞可靠的文本结果。

## 4. 标准工作流

### 4.1 单次查询与完整菜谱

1. 用 `search_recipes` 进行硬过滤和候选发现；若请求针对正文处理方法，可先用 `grep_recipe_docs`。
2. 返回少量候选时保留名称、耗时、核心食材、过敏原、匹配原因、ID 和版本。
3. 用户选择某道菜或直接请求完整做法时，调用 `read_recipe`；不要把搜索摘要扩写成完整步骤。若结果包含目标份数和待采购食材，默认汇总采购并报价；除非用户明确拒绝，最后生成 HTML。

### 4.2 周期餐单

1. 确认阻塞信息并搜索足量候选。
2. 对进入候选方案的菜谱按目标份数读取确切版本和完整正文；Agent 负责组合和权衡，MCP 不负责宽泛生成。
3. 汇总完整方案的采购；除非用户明确拒绝报价，否则从待采购项生成报价请求。没有地区时省略 `region`，使用全国参考。
4. 调用 `validate_meal_plan` 校验完整范围和硬约束。
5. `errors` 非空时修正候选并重新计算受影响的采购、价格和校验；最多自动修正两轮。
6. 校验通过后，用 `render_meal_plan_html` 渲染菜单、烹饪卡、采购和可选价格数据；返回 HTML 文件与聊天摘要，并披露 warnings 和 assumptions。

一个日期和餐次可以包含多道不同菜。每道菜作为一条 `meals` 输入，共享相同 `date` 和 `meal_type`；同一餐次不得重复添加相同 `recipe_id`。`max_cooking_minutes` 当前按单道菜校验，不推断并行烹饪后的整餐耗时。

目标份数必须贯穿读取、采购与校验：

- `read_recipe.servings` 使用用户目标份数；最终食材展示取 `scaled_ingredients`。
- 最终餐单的读取应包含原始 Markdown 正文或等价的完整步骤字段。搜索摘要不能支撑烹饪做法；读取失败时应改选可完整读取的菜谱，或把结果降级为缺少做法的候选，不能声称已经交付可执行餐单。
- `aggregate_shopping_list.items[].servings` 与读取和校验使用相同份数。
- 原始 `parsed.ingredients` 只代表菜谱基准份数；目标份数不同的时候，不得把它与缩放后的 `to_buy` 并列为同一数量。
- 同一食材若同时展示两种单位，必须来自同一个缩放结果并校验换算关系；无法可靠换算时只保留工具原值与警告。

报价必须从采购汇总结果确定性派生：

- 把 `groups[].items[]` 中 `ingredient_id` 非空、`to_buy.quantity` 大于零且 `to_buy.unit` 非空的项目映射为报价输入的 `ingredient`、`quantity` 和 `unit`。
- 用户提供地区时传入原始地区；未提供时省略 `region`，服务端以“全国”作为请求地区。不得为了默认报价单独中断流程追问地区。
- `ingredient` 使用标准 `ingredient_id`，不使用展示名称。`ingredient_id` 为空、数量未量化或单位缺失的项目不发送给报价工具，统一列入无法估价项。
- 默认允许省级市场无数据时返回全国参考价，再以明确标记的跨地区维护者基准补充包装品等缺口；用户明确要求“只看本地/本省价格”时设置 `allow_national_fallback: false`，此时禁止全部非省级回退。无论是否允许回退，都不得把全国价或其他城市基准算作省级命中。
- 库存已完全覆盖且 `to_buy.quantity` 为零的项目不报价。
- 仅汇总 `total_price` 非空的报价。存在 `unmatched`、`total_price: null` 或未发送项目时，把金额称为“已估价小计”，并明确总预算仍不完整；不得把未知项按零元处理。
- 每条报价的采购量与单位取 `requested_quantity`；`unit` 是单价计价单位，禁止把二者拼成同一个数量。优先使用工具返回的 `summary.priced_subtotal`、省级命中数、全国回退数、跨地区基准数、`budget_status` 和 `complete`，不让 Agent 自行推断覆盖率。
- `region_match: true` 表示报价至少匹配请求地点所在省级行政区；实际地区以 `matched_region`、`region_scope` 和 `region_code` 为准。全国回退必须读取为参考价，不能因为有 `total_price` 就改称本地价。
- `summary.complete` 表示全部请求项都有可换算且至少省级匹配的总价；它不等于价格口径足以验证硬预算。还要把未发送报价的未标准化/未量化采购项计入整体缺口。
- 有硬预算时，把总价区间、`complete` 和 `budget_status` 传入最终校验。只有 `budget_status: verified` 才能执行硬预算通过判断；`reference_only` 或 `incomplete` 均返回 `BUDGET_UNVERIFIED`，方案只能称为“预算参考候选”。没有预算上限时只报告参考花费，不声称“预算内”。

正式餐单中的每道菜、配菜和主食都必须来自实际读取的 `recipe_id + version`，并进入采购汇总和校验。不得在菜名后擅自追加“配米饭”等未追溯项目；可以把它列为明确未纳入采购和预算的可选建议，但不能混入正式方案。

### 4.3 局部修改

1. 复制当前方案作为基线，锁定未点名餐次。
2. 缺货、偏好或预算原因优先调用 `find_replacements`，再为目标餐次按目标份数读取完整正文并替换候选；共享食材、预算或硬约束造成的依赖变化可以传播，但必须说明。
3. 重新汇总完整方案的采购；除非用户明确拒绝价格，否则重新报价并更新总区间。预算关系本身不证明更便宜，必须比较新报价。
4. 校验修改后的完整方案。
5. 重新渲染 HTML，返回完整新产物和差异摘要。未点名且不受依赖影响的餐次必须逐项保持不变。

## 5. 修正、降级与停止

- 正式知识库无匹配时，不得创造 `recipe_id` 或伪装成已发布菜谱。说明没有正式结果，并询问用户是否接受清晰标注的 AI 草稿。
- 校验错误最多自动修正两轮。仍无解时停止，指出冲突并给出最小放宽建议；不要静默放宽硬约束。
- `RATE_LIMITED`、`TIMEOUT` 或 `PROVIDER_UNAVAILABLE` 可以按错误的 `retryable` 和用户时效要求做有限重试；同一步最多一次，随后降级或报告不可用。
- 价格失败不能阻止无价格餐单和采购量交付。价格未知时保持未知，不用零代替。
- 单位不可换算或数量不精确时保留工具警告，不伪造精确值。
- 任一工具缺失或不可连接时，明确指出未完成的能力和受影响结果，不根据记忆伪造工具事实。

## 6. 不变量

- 最终正式菜谱始终携带工具实际返回的 `recipe_id` 和 `version`。
- 已知硬约束始终传给搜索和最终校验；过敏原冲突不得作为警告降级。
- `validate_meal_plan.errors` 非空时不得声称方案已通过。
- 价格始终是区间，并携带地区、来源类型、数据时间和可信度；无法估价项单独列出。
- 不把 AI 草稿描述为知识库菜谱，不让未经审核内容获得 `published` 身份。
- 不在输出中泄露 MCP Token、宿主配置或不必要的健康信息。
