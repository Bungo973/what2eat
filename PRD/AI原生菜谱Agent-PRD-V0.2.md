### 1.1 相对 V0.1 的主要变化

- 明确 Skill 面向通用 Agent 宿主，不以 Codex 为唯一目标。
- 明确产品和工程重点是 MCP 工具契约及可维护的菜谱知识库，Skill 保持轻量。
- 菜谱知识库确定采用 Markdown 文件；每个菜谱版本是一份包含 YAML frontmatter 的完整文档。
- 增加运行时结构化索引与正文 grep 的职责区分，P0 不引入向量数据库。
- 公共 MCP 工具收敛为六个：`search_recipes`、`grep_recipe_docs`、`read_recipe`、`aggregate_shopping_list`、`validate_meal_plan`、`quote_ingredient_prices`。
- `normalize_ingredients` 改为 MCP 内部能力，不再要求 Agent 单独调用。
- 增加面向用户的黑盒输入、追问、输出和失败契约。
- 未提出预算时默认不设预算上限；未要求估价时不询问地区、不调用价格工具。
- 价格区间是固定产品行为，不再询问用户是否接受参考区间。
- 价格能力采用 provider 适配器，P0 以单城市基准价格为可接受起点。

## 2. 产品定义

产品从固定页面和多步骤向导的一周食谱 Web 应用，调整为供通用 Agent 调用的菜谱领域能力。

用户在任意兼容宿主中自然表达需求，Agent 负责理解、追问、权衡和编排；MCP 提供可信、可追溯、可确定性执行的菜谱与采购能力；菜谱知识库由维护者以 Markdown 文档持续维护。

产品价值是：

> 为兼容 Agent 提供可信、可维护的菜谱知识和食谱规划工具，使 Agent 能生成可解释、可修改、可校验的餐单与采购清单。

### 2.1 产品重点

优先级从高到低为：

1. 菜谱知识的质量、版本和可追溯性；
2. MCP 工具契约的稳定性与确定性；
3. 硬约束校验、采购汇总和价格披露；
4. 通用 Skill 的工作流指导和宿主适配；
5. 后续可选的可视化或消费者客户端。

## 3. 目标与非目标

### 3.1 P0 目标

- 提供一份可安装、可引用、面向通用 Agent 的菜谱规划 Skill。
- 提供一个需要鉴权的远程 MCP 服务。
- 建立以 Markdown 为唯一事实源的菜谱知识库。
- 维护者能够校验、发布、升级和归档菜谱版本。
- Agent 能检索和读取正式菜谱、编排周期餐单、局部换菜、汇总采购量并校验硬约束。
- 在用户需要时提供带地区、来源、时间和可信度的参考价格区间。
- 对价格时效、数据缺口、非精确数量、AI 草稿和无解约束做明确披露。
- 至少覆盖单次菜谱查询、周期规划、剩余食材处理和局部换菜。

### 3.2 P0 非目标

- 不开发面向普通用户的完整聊天网页。
- 不建立用户注册、登录、社区投稿或社交体系。
- 不允许公共调用者修改正式菜谱库。
- 不承诺价格实时、精确或覆盖所有城市和渠道。
- 不做下单、配送、支付或电商导购闭环。
- 不提供医疗级营养建议。
- 不在 MCP 内部调用大模型完成宽泛的方案生成。
- 不引入向量数据库或复杂排程优化器。
- 不建设菜谱管理 Web 后台。

## 4. 总体架构与职责

```text
用户
  ↓ 自然语言
Agent + 通用 Skill
  ├─ 识别任务类型
  ├─ 从当前消息和上下文提取需求
  ├─ 只追问阻塞信息
  ├─ 调用 MCP 并编排方案
  ├─ 处理局部修改
  └─ 输出用户可读结果
  ↓
远程 MCP 服务
  ├─ 结构化索引检索
  ├─ Markdown 正文搜索与读取
  ├─ 食材标准化与采购汇总
  ├─ 价格 provider、缓存与降级
  └─ 方案确定性校验
  ↓
Markdown 知识库
  ├─ 版本化菜谱文档
  ├─ 标准食材与别名
  ├─ 单位换算规则
  └─ 地区基准价格
```

### 4.1 Agent 与 Skill

- Skill 是平台无关的领域工作方法，不保存动态事实或凭证。
- Skill 告诉 Agent 何时触发、需要提取什么、何时追问、调用哪些工具、何时停止，以及如何表达结果。
- Agent 负责自然语言理解、偏好权衡、候选编排、自动修正和局部修改。
- 核心行为规范不得依赖 Codex 专属语法；宿主专用包装只做适配。

### 4.2 MCP

- MCP 提供事实、检索和确定性操作，不替代 Agent 的通用推理。
- 不提供 `generate_plan(user_message)`、`give_solution()` 等宽泛工具。
- 工具保持窄、批量友好、可组合、可验证并返回结构化结果。
- 公共工具只读；维护能力通过受保护的本地 CLI 或管理接口完成。

### 4.3 Markdown 知识库

- Markdown 文件是菜谱内容的唯一事实源。
- YAML frontmatter 保存需要检索、换算和校验的结构化字段。
- Markdown 正文保存步骤、替换建议、储存和食品安全说明。
- 运行时索引、缓存和数据库均为可删除重建的派生数据，不得反向成为内容事实源。

## 5. 用户黑盒契约

### 5.1 支持的任务类型

- 查询一道菜或获取少量候选；
- 根据现有食材推荐做法；
- 创建周期餐单；
- 查询食材参考价格；
- 修改现有方案中的局部或全部餐次；
- 查看某道菜的完整步骤、替换和注意事项。

### 5.2 周期餐单的阻塞信息

生成周期餐单前，Agent 必须从当前消息和历史上下文中确认：

- 覆盖的日期、天数或范围；
- 需要安排的餐次；
- 用餐人数或目标份数；
- 是否存在过敏、严格忌口、宗教限制或明确饮食方式。

用户明确回答“没有过敏或忌口”视为已确认。不得重复询问已经提供的信息。

### 5.3 条件性阻塞信息

- 用户提出硬预算时，需要确认金额、币种以及它是硬上限还是参考目标。
- 用户要求估价时，需要确认地区，至少精确到城市。
- 用户指定渠道时，需要确认商家或渠道。
- 用户将烹饪时间或厨具作为硬约束时，需要获得明确值。
- 局部修改依赖当前方案；若上下文中没有可识别方案，需要用户提供或重新生成。

### 5.4 非阻塞信息与默认值

- 用户未提预算：默认不设预算上限，不额外追问。
- 用户未要求价格：不询问地区，不调用价格工具。
- 价格固定返回参考区间，直接披露其性质，不询问用户是否接受区间。
- 菜系、辣度、重复度、食材复用、总烹饪时间和已有库存属于软偏好，只有会显著改变结果时才追问。
- 是否接受 AI 草稿不提前询问；仅在正式知识库无解时询问或提供明确选项。

### 5.5 最少追问原则

- 先提取后追问，不要求用户填写完整表单。
- 一次集中询问一至三个最关键问题。
- 单次查询不启动周期规划问卷。
- 可以采用低风险默认值时，应说明假设并继续。
- 过敏原、宗教限制和严格饮食方式不得猜测。

### 5.6 Agent 内部需求对象

Agent 应在上下文中维护以下概念，但不要求用户直接填写结构化对象：

```yaml
intent: create_meal_plan
scope:
  dates: []
  meal_types: []
servings: 2
hard_constraints:
  allergens: []
  excluded_ingredients: []
  dietary_patterns: []
  max_cooking_minutes: null
  unavailable_equipment: []
budget:
  mode: none
  amount: null
  currency: CNY
pricing:
  region: null
  merchant: null
inventory: []
preferences:
  cuisines: []
  spicy_level: null
  prioritize_reuse: true
  avoid_repetition: true
draft_policy:
  allow_ai_draft: null
```

字段应区分用户事实、采用的默认值和仍未确认的信息。

## 6. 用户输出契约

输出遵循“先给结果，后给依据”，不暴露不必要的工具调用细节。

### 6.1 候选菜谱

- 菜谱名称；
- 预计耗时；
- 核心食材；
- 与需求的关键匹配项；
- 已知过敏原；
- 菜谱 ID 和版本；
- AI 草稿标识。

### 6.2 周期餐单

- 日期与餐次；
- 菜谱名称、ID 和版本；
- 预计烹饪时间；
- 选择理由；
- 必要的替代建议；
- AI 草稿标识。

### 6.3 采购清单

- 标准食材名称；
- 总需求量和单位；
- 已有数量；
- 建议采购量；
- 关联日期和菜谱；
- 非精确量或换算警告。

采购清单优先按蔬菜、肉蛋奶、主食、调味品等类别分组。

### 6.4 价格与预算

仅在用户要求估价或提出预算时返回：

- 预计总价区间；
- 是否满足硬预算；
- 地区和渠道；
- 数据来源类型；
- 查询或基准时间；
- 可信度；
- 无法估价的食材及原因。

### 6.5 方案摘要

- 已满足的硬约束；
- 采用的默认值和假设；
- 主要取舍；
- 仍存在的警告；
- 数据缺口和低可信结果。

### 6.6 修改结果

局部修改后返回：

- 修改后的完整产物；
- 本轮变更摘要；
- 采购量变化；
- 预算变化；
- 新增或解除的警告。

未被点名且不受依赖影响的餐次必须保持不变。

### 6.7 失败与无解

- 知识库无匹配时，不伪造菜谱 ID；说明没有正式菜谱，并询问是否接受 AI 草稿。
- 硬约束无解时，指出冲突并给出最小放宽建议。
- 价格不可用时，继续返回餐单和采购量，价格标记为未知。
- 单位无法换算时，保留原始描述并返回警告。
- 校验存在错误时，不得把方案包装成最终可执行结果。
- 工具不可用时，明确说明缺少的能力，不假装完成完整流程。

## 7. Skill 产品规格

### 7.1 建议名称与描述

名称暂定：`meal-planning`

建议描述：

> 使用已连接的菜谱知识库和价格工具，为用户查询菜谱、规划周期餐单、生成采购清单并按约束修改方案。适用于做饭安排、菜谱查询、预算规划、剩余食材处理或换菜请求。

### 7.2 Skill 内容

- 任务类型识别；
- 信息提取、默认值与最少追问规则；
- 硬约束和软偏好的处理方式；
- 六个 MCP 工具的选择与调用顺序；
- 最大两轮自动修正和停止条件；
- 无结果、低可信价格、限流和超时的降级策略；
- 用户输出契约；
- 不伪造知识库引用、不隐藏 AI 草稿等行为边界。

### 7.3 推荐工作流

```text
识别任务并提取已知信息
  ↓
是否存在阻塞信息
  ├─ 是：集中追问一至三个问题
  └─ 否：继续
  ↓
search_recipes / grep_recipe_docs
  ↓
read_recipe
  ↓
Agent 选择或编排候选
  ↓
aggregate_shopping_list（需要采购清单时）
  ↓
quote_ingredient_prices（需要预算或估价时）
  ↓
validate_meal_plan（形成方案时）
  ↓
输出结果、依据、假设和警告
```

自动修正最多两轮。仍无法满足硬约束时停止，并说明冲突及最小放宽建议。

## 8. 公共 MCP 工具

### 8.1 `search_recipes`

用于周期规划和一般菜谱发现，查询运行时结构化索引。

主要输入：

- `query`；
- `meal_types`；
- `include_ingredients`；
- `exclude_ingredients`；
- `dietary_constraints`；
- `exclude_allergens`；
- `max_total_minutes`；
- `equipment`；
- `difficulty`；
- `limit` 和分页游标。

主要输出：

- 菜谱 ID 和实际版本；
- 名称、摘要和核心食材；
- 预计时间、标签和已知过敏原；
- 匹配字段或可解释的匹配原因。

规则：

- 默认只返回当前 `published` 版本；
- 硬过滤先于全文匹配和排序；
- 检索摘要不能代替完整菜谱；
- P0 使用 frontmatter 字段、标签和普通全文索引，不使用向量数据库。

### 8.2 `grep_recipe_docs`

用于搜索菜谱正文中的词语、步骤、处理方法和来源片段，是 `search_recipes` 的补充工具。

主要输入：

- `pattern`；
- 可选 `recipe_ids`；
- 可选搜索章节；
- `limit` 和分页游标。

主要输出：

- 菜谱 ID 和版本；
- 命中章节；
- 行号或定位信息；
- 有长度上限的上下文片段。

规则：

- 只能搜索菜谱知识库，不能接受任意文件系统路径；
- 默认只搜索当前已发布版本；
- P0 只支持普通文本匹配，不直接执行调用者提供的任意正则；
- 限制返回数量和片段长度。

### 8.3 `read_recipe`

按 `recipe_id + version` 读取一份完整菜谱文档。

主要输入：

- `recipe_id`；
- 可选 `version`，缺省为当前发布版本；
- 可选目标份数；
- `format: raw | parsed | both`。

主要输出：

- 原始 Markdown；
- 解析后的结构化字段；
- 实际读取版本；
- 按目标份数换算的食材数量；
- 换算和非精确量警告。

规则：不接受任意路径；读取历史版本时必须返回确切版本，不静默替换为最新版。

### 8.4 `aggregate_shopping_list`

确定性汇总餐单所需食材并扣除已有库存。

主要输入：

- 菜谱 ID、版本和份数；
- 用户已有食材和数量。

主要输出：

- 标准食材名称；
- 总需求、已有量和待采购量；
- 关联菜谱与日期；
- 单位换算和非精确量警告。

食材别名、标准 ID 和单位换算在工具内部处理，不要求 Agent 预先调用独立标准化工具。

### 8.5 `validate_meal_plan`

校验 Agent 已生成的候选方案，不负责生成方案。

校验范围：

- 日期和餐次是否完整；
- 菜谱版本是否存在且可用；
- 过敏原、忌口和饮食方式；
- 硬预算；
- 厨具和烹饪时间；
- 数量或单位异常；
- 重复度和多样性等软警告。

输出：

- `errors`：必须修正的硬约束冲突；
- `warnings`：用户可以接受的软问题；
- `assumptions`：因信息不足采用的假设；
- `validated_at`。

### 8.6 `quote_ingredient_prices`

查询一组标准食材在指定地区和可选渠道的参考价格。

主要输入：

- 地区；
- 食材 ID、数量和单位；
- 可选渠道；
- 可选价格时效要求。

主要输出：

- 单价或总价区间；
- 币种；
- 地区和商家；
- 来源标识或链接；
- 查询时间；
- `realtime | cached | benchmark` 数据类型；
- `low | medium | high` 可信度；
- 无法匹配的食材及原因。

规则：不得伪造精确价格；完全无数据时返回未知，不使用零元代替。

### 8.7 统一错误契约

工具错误至少包含：

```yaml
code: INVALID_ARGUMENT
message: 面向 Agent 的简洁说明
retryable: false
request_id: optional
details: {}
```

错误码至少覆盖：

- `INVALID_ARGUMENT`；
- `NOT_FOUND`；
- `CONFLICT`；
- `UNAUTHORIZED`；
- `FORBIDDEN`；
- `RATE_LIMITED`；
- `TIMEOUT`；
- `PROVIDER_UNAVAILABLE`；
- `DATA_INVALID`。

## 9. Markdown 菜谱知识库

### 9.1 文件组织

每个菜谱版本是一份完整 Markdown 文档：

```text
recipes/
├─ tomato-eggs/
│  ├─ v1.md
│  └─ v2.md
└─ cola-chicken-wings/
   └─ v1.md

drafts/
└─ tomato-eggs-v3.md
```

- 已发布文件不可原地修改。
- 修改正式菜谱时创建更高版本文件。
- 草稿位于 `drafts/`，不进入公共搜索和读取默认范围。
- 当前状态由最高的非草稿版本决定。
- 归档时创建更高版本的完整快照并设置 `status: archived`，不修改旧版本。
- `read_recipe` 仍可按版本读取归档前的历史内容。

### 9.2 单文档结构

```markdown
---
schema_version: 1
recipe_id: tomato-eggs
version: 2
status: published
name: 番茄炒蛋
summary: 十五分钟完成的家常番茄炒蛋
servings: 2
prep_minutes: 5
cook_minutes: 10
meal_types: [lunch, dinner]
difficulty: easy
equipment: [wok]
tags: [quick, home-style]
dietary_labels: [vegetarian]
allergens: [egg]
ingredients:
  - id: tomato
    name: 番茄
```

### 9.3 字段规则

- `recipe_id` 在全部版本中稳定不变。
- `version` 为递增正整数。
- `status` 为 `draft | published | archived`。
- `servings`、时间和可量化食材必须使用数值。
- 单位使用受控标准值，例如 `g`、`kg`、`ml`、`l`、`piece`。
- 无法量化的食材使用 `quantity: null` 并提供 `notes`，汇总时必须产生警告。
- `allergens` 在发布时根据食材目录自动复核，不能只依赖人工填写。
- YAML 是机器字段的唯一事实源；正文不重复维护另一份食材表。
- 正文至少包含非空、有序的“做法”章节。

### 9.4 食材目录与单位规则

P0 可使用一份 Markdown 文档保存标准食材、别名、默认采购单位、单位换算和过敏原标签，其 YAML frontmatter 为机器事实源。

食材目录至少包含：

```text
id
canonical_name
aliases[]
category
default_purchase_unit
conversions[]
allergen_tags[]
price_query_terms[]
```

不可互换的食材不得仅因名称相似而合并。

### 9.5 运行时索引与 grep

MCP 启动或构建时：

1. 扫描全部菜谱 Markdown；
2. 解析 YAML frontmatter；
3. 执行 schema、版本、食材、单位和过敏原校验；
4. 确定每个菜谱的当前状态和当前发布版本；
5. 建立可删除重建的内存或 SQLite 索引；
6. 将正文提供给受限全文搜索。

结构化索引用于状态、餐次、时间、厨具、忌口和过敏原等确定性过滤；grep 用于搜索步骤、处理方法和正文片段。两者互补，不互相替代。

P0 数据规模较小时优先使用内存索引或 SQLite FTS，不引入向量检索。

## 10. 价格能力

### 10.1 产品定位

价格是参考信息，不是承诺价格。输出必须是区间并携带证据，不用虚假的精确总额营造确定感。

### 10.2 Provider 架构

```text
quote_ingredient_prices
  ↓
PriceProvider
  ├─ benchmark       维护者提供的地区基准价格
  ├─ cached          有效期内的历史结果
  ├─ external_mcp    可用的外部价格 MCP
  ├─ retailer_api    零售商或数据服务接口
  └─ unknown         无数据时的结构化失败
```

P0 至少实现一个首发城市的基准价格。现成第三方 MCP 可以作为 provider 接入，但不得让核心工具契约依赖单一第三方。

### 10.3 缓存与降级

- 相同地区、食材、渠道和规格在有效期内优先使用缓存。
- 生鲜与常温食品可以使用不同有效期。
- 实时查询失败时退回缓存，再退回基准价格。
- 每次降级保留数据类型、时间和可信度。
- 无任何数据时返回未知。

## 11. 管理与发布流程

P0 不向普通 MCP 调用者暴露管理工具。维护者通过受保护的 CLI 完成：

```text
recipe validate
recipe create-draft
recipe publish
recipe archive
recipe rebuild-index
```

发布必须：

- 校验 frontmatter schema；
- 校验 ID 和版本唯一性；
- 校验食材 ID、数量和单位；
- 复核过敏原和饮食标签；
- 校验做法非空；
- 确认目标版本高于已有版本；
- 将草稿生成或移动为不可变发布文档；
- 重建索引并运行契约测试。

## 12. 安全、隐私与成本

### 12.1 鉴权与权限

- 远程 MCP 默认需要访问凭证。
- 公共只读工具与维护者写入能力分离。
- 凭证不得写入 Skill、Markdown 知识库、日志或用户产物。
- 首版个人或小范围测试可使用 Bearer Token；公开多用户发布时再评估 OAuth。

### 12.2 输入与文件安全

- `grep_recipe_docs` 和 `read_recipe` 不接受任意文件路径。
- 服务端根据 recipe ID 和版本解析受控路径，并阻止目录穿越。
- 所有工具输入按不可信输入校验。
- 限制搜索结果、读取大小、批量食材数量和自动重试次数。

### 12.3 日志与隐私

- 日志记录请求 ID、工具、耗时、结果类型和错误码。
- 不记录凭证或不必要的个人饮食、健康信息。
- 价格查询单独限流并优先使用缓存。

### 12.4 内容安全

- 过敏原冲突属于硬错误，但产品不能替代专业医疗建议。
- 菜谱发布前检查基础生熟食、加热、冷藏和交叉污染提示。
- 未审核内容不得标记为正式知识库菜谱。

### 13.1 必须实现

## 14. 验收标准

### 场景 1：最少追问

用户已提供五天晚餐、两人和无过敏忌口时，Agent 不重复询问这些字段。用户未要求价格时，不询问地区或预算。

### 场景 2：正式菜谱追溯

最终方案中的每道正式菜谱都能追溯到 `recipe_id` 和确切版本。知识库无合适结果时不伪造引用。

### 场景 3：结构化过滤与正文搜索

`search_recipes` 能确定性排除过敏原和超时菜谱；`grep_recipe_docs` 能找到做法中包含指定处理方式的正文片段。

### 场景 4：完整读取

`read_recipe` 能返回原始 Markdown、解析字段或两者，并能按 ID 和历史版本读取。

### 场景 5：硬约束校验

候选方案包含用户过敏原时，`validate_meal_plan` 返回错误，Agent 不将其作为最终可执行方案。

### 场景 6：采购汇总

多个菜谱中的标准食材能正确合并并扣除库存；非精确量和不可换算单位返回警告。

### 场景 7：参考价格披露

预算结果包含价格区间、地区、来源类型、时间和可信度；使用基准数据时明确标记为非实时价格。

### 场景 8：局部修改

用户只要求更换周三晚餐时，其他无依赖餐次保持不变，并返回采购及预算变化摘要。

### 场景 9：价格失败

实时价格 provider 超时或限流时退回缓存或基准数据；完全无数据时明确未知，不编造价格。

### 场景 10：无解

硬约束导致无解时，Agent 最多自动修正两轮，然后指出冲突并给出最小放宽建议。

### 场景 11：版本不可变

发布新版本时创建新 Markdown 文件，旧版本内容不被覆盖；归档后仍可读取历史版本。

## 15. 成功指标

- MCP 工具调用成功率；
- 菜谱文档 schema 校验通过率；
- 检索候选进入最终方案的命中率；
- 硬约束漏检率，目标为零；
- 采购汇总单位异常率；
- 价格查询及缓存命中率；
- 方案首次生成后无需修改的比例；
- 局部修改时未点名餐次的保留率；
- 单任务 MCP 调用次数和返回上下文体积；
- 菜谱从草稿到发布的校验通过率。

## 17. 实施顺序

1. 定义菜谱 frontmatter、食材目录、计划和工具 schema。
2. 实现 Markdown 解析、校验、版本判断和发布 CLI。
3. 准备覆盖不同餐次、时间和饮食限制的种子菜谱。
4. 实现结构化索引、`search_recipes`、`grep_recipe_docs` 和 `read_recipe`。
5. 实现内部食材标准化、采购汇总和方案校验。
6. 加入首发城市基准价格、provider 接口和缓存。
7. 编写通用 Skill 与平台无关行为规范。
8. 使用真实对话场景做端到端测试，重点验证最少追问、硬约束和局部修改。
9. 再决定是否接入外部价格 MCP、实时零售接口、向量检索或可视化客户端。

## 18. 定稿结论

P0 采用“轻量通用 Skill + 确定性 MCP + Markdown 菜谱知识库”的产品形态。

Markdown 负责可维护、可审阅和可追溯的知识内容；运行时索引负责结构化过滤；受限 grep 负责正文搜索；Agent 负责编排和权衡；MCP 负责事实、汇总、价格与硬约束校验。

该边界既保留 Agent 原生交互的灵活性，也避免把过敏原、版本、单位和预算等关键正确性完全交给语言模型。
