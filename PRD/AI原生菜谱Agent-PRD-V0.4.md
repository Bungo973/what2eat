# AI 原生菜谱 Agent PRD V0.4

## 文档信息

- 版本：V0.4
- 日期：2026-08-24
- 状态：可实施
- 上一版本：V0.3

## 相对 V0.3 的变更

1. 完整菜谱或正式餐单默认给出参考报价；用户可明确选择不报价。
2. 未提供地区时不为报价单独追问，默认查询“全国”参考价；用户给出省/市时优先返回对应省级数据，并披露回退层级。
3. 默认交付自包含 HTML 计划页，同时保留简短 Markdown 摘要与降级路径。
4. Obsidian Vault `knowledge/menu/` 成为知识库默认根目录。
5. 新增食材替换、菜谱关系契约，以及 `find_replacements`、`render_meal_plan_html` 两个窄 MCP 工具。

## 1. 目标

让用户用自然语言获得可追溯、可执行、带采购和参考价格的菜谱或餐单，并能在食材缺货、偏好变化或预算压力下可靠地局部调整。Obsidian 面向维护者提供可浏览、可链接的知识编辑体验；MCP 面向 Agent 提供稳定、确定性的结构化能力。

## 2. 默认用户体验

### 2.1 首次接触

只问“想怎么安排吃的？”，可附不超过两个自然语言示例。用户给出可执行需求后直接处理，不展示工具清单或调用过程。

### 2.2 完整结果

正式选定一道或多道菜后，结果默认包含：

1. 菜单或餐次安排；
2. 目标份数食材与完整可执行步骤；
3. 采购清单；
4. 参考价格与覆盖说明；
5. 约束、假设、警告；
6. 自包含 HTML 文件。

用户明确“不要报价/不需要价格”时跳过报价。仅浏览候选、只问做法事实或没有待采购食材时，可以不生成价格与 HTML。

### 2.3 地区与预算语义

- 用户提供地区：优先使用对应省级/城市市场数据。
- 用户未提供地区：以“全国”作为请求地区，返回全国批发参考或可用基准，不阻塞方案生成。
- 全国价、跨地区价和批发价必须明确标为参考，不得描述成当地零售成交价。
- 用户未给预算时，没有预算上限；报价仅是花费参考。
- 只有用户明确给出金额并声明硬上限时，预算才是硬约束。覆盖不完整或只含参考数据时，硬预算保持“未验证”。

## 3. 产品边界

- Agent 负责需求理解、最少追问、组合、取舍、工具编排和表达。
- MCP 负责菜谱事实、检索、标准化、替换候选、采购汇总、价格、校验和 HTML 渲染。
- MCP 不生成宽泛自然语言餐单，不决定用户偏好，不把动态价格写回菜谱。
- HTML 渲染器只渲染已准备好的结构化结果，不重新规划、计算或报价。

## 4. MCP 公共工具

V0.4 提供八个向后兼容的公共工具：

| 工具 | 职责 |
| --- | --- |
| `search_recipes` | 搜索和硬过滤已发布菜谱 |
| `grep_recipe_docs` | 定位正文词语、步骤和处理方法 |
| `read_recipe` | 读取确切版本及目标份数事实 |
| `aggregate_shopping_list` | 汇总采购并扣减库存 |
| `quote_ingredient_prices` | 按标准食材和采购量报价；地区可选，缺省全国 |
| `validate_meal_plan` | 确定性校验完整方案 |
| `find_replacements` | 返回已发布食材替换规则和通过硬过滤的整菜候选 |
| `render_meal_plan_html` | 将已验证的结构化产物渲染为自包含 HTML |

现有六个工具的名称和 schema 保持兼容。新增能力以新工具提供，不扩张成 `generate_plan(user_message)`。

## 5. Obsidian 知识库

### 5.1 目录

```text
knowledge/menu/
├─ 首页.md
├─ 维护说明.md
├─ .obsidian/
├─ recipes/<recipe_id>/v<version>.md
├─ drafts/
├─ ingredients/ingredients.md
├─ substitutions/<substitution_id>-v<version>.md
├─ relations/<relation_id>-v<version>.md
└─ prices/
```

### 5.2 双层关系

- Obsidian 双向链接用于维护者导航和知识发现。
- YAML frontmatter 中稳定 ID、版本、状态与关系字段是 MCP 的机器事实源。

两者可以共存，但 MCP 不解析自然语言双链来猜关系。

### 5.3 替换与预算调整

食材替换规则必须限定上下文，并描述比例/省略方式、步骤变化、过敏原变化、风味口感影响和证据。整菜替代关系仅产生候选；任何因预算或缺货导致的换菜都必须重新读取菜谱、汇总采购、报价并校验，禁止把“通常便宜”固化为运行时价格结论。

### 5.4 发布规则

已发布菜谱和关系不可原地覆盖；修改时新增版本。AI 生成内容默认是草稿，经 schema 校验和人工审核后方可发布。

## 6. HTML 产物

- UTF-8、单文件、自包含 CSS，不依赖外部 CDN 或脚本。
- 至少包含菜单、菜谱卡、采购表、价格表（有报价时）和提示。
- 适配窄屏与打印；所有用户/知识库文本均转义。
- MCP 返回文件名、MIME、HTML 内容和本地产物路径。宿主不能展示/附加文件时，降级为 Markdown 完整结果。

## 7. 验收标准

1. 默认知识路径指向 `knowledge/menu`，现有已发布菜谱版本和内容不因迁移而改变。
2. 完整餐单未给地区时，报价请求可省略 `region` 并返回明确标注的全国参考。
3. 用户给地区时，逐项披露请求地区、匹配地区、层级、来源和回退。
4. 用户未给预算时仍可报价，但校验器不产生预算通过结论。
5. `find_replacements` 不绕过过敏、忌口、厨具和时间硬过滤；预算替换后要求重新报价。
6. HTML 输出转义不可信文本，包含清晰菜单、烹饪卡、采购与价格表。
7. 八个工具的输入输出均通过 schema 与 MCP 契约测试；Skill 覆盖单次查询、周期规划和局部换菜。
