# AI 原生菜谱 Agent PRD V0.5

## 文档信息

- 版本：V0.5
- 日期：2026-08-24
- 状态：设计方向，未实施——需评审通过后再排入实施计划；V0.4 已实施范围不受影响，继续作为当前运行基线
- 上一版本：V0.4

## 相对 V0.4 的变更

V0.4 上线后，维护者在 Obsidian 中实际使用知识库时发现 `relations/`（菜谱关系）无法回答一类真实存在的问题：食材缺货或不想要某食材时，如何快速判断哪些菜受影响、能不能省/能不能换。排查后确认这是**结构性缺口**，不是数据没写全——`recipe-relation.schema.json` 从设计上就没有食材维度的字段，而承担食材级语义的 `substitution.schema.json` 虽然预留了 `valid_context.roles` 枚举，但因为菜谱 `ingredients[]` 缺少对应的 `role` 字段，判断逻辑（`packages/recipe-domain/src/replacement.ts`）里通用角色规则的分支实质上从未被激活，导致替换规则只能退化成"一条规则绑一道菜"。

V0.5 提出的方案，**大部分是恢复并细化 V0.3 §9.2–9.4 已经设计但未进入 V0.4 实施范围的食材角色模型**，同时新增三个 V0.3 没有覆盖的概念：`defines_dish`（换掉是否等于变成另一道菜）、食材功能分组（评估后决定暂不推进，原因见"设计方向 3"）、菜谱关系的结构化 `balance_dimensions`（把"为什么搭"从自由文本变成可推理维度）。本版本不改变任何已实施的 MCP 工具契约或 V0.4 验收标准，只新增一节设计方向，明确标注未实施；设计方向落地时预计还需要同步更新 Skill 的用户表达行为（`specs/behavior/`、`skills/meal-planning/`），本版本先只锁定数据模型方向，行为层改动留待实施阶段单独评审。

## 背景：用户实际会怎么问

先于设计方案，梳理了用户会怎么问食材相关问题，分成四类，代表未来验收场景的雏形：

| 类别 | 例子 | 现状 |
| --- | --- | --- |
| 食材→菜谱发现 | "我有西红柿、牛肉，能做什么？" | `search_recipes` 的 `include_ingredients` 已支持硬过滤，但没有"覆盖率"排序（哪些菜只差一两样） |
| 缺食材→计划影响面 | "漏买了土豆，计划要重定吗？" | 哪些菜用到土豆已可查（`aggregate_shopping_list` 的 `used_in`），但"能不能省/能不能换"缺规则覆盖 |
| 单菜单食材可省可换 | "不想吃香菜，这道菜能不放吗？" | `find_replacements` 已支持，但仅在已发布规则精确覆盖该菜谱时才有结果 |
| 换后下游重算 | "换了鸡肉，预算会不会超？" | Skill 行为已要求换菜后重新报价校验，属于流程正确性，非数据模型问题 |

其中第二、三类是本次设计方向要解决的核心缺口，第一类需要新的检索排序能力（非本次范围，见"非目标"），第四类已有正确的流程约束，不需要数据模型变更。

## 设计方向

### 1. 菜谱食材补充角色与身份字段

`recipe-frontmatter.schema.json` 的 `ingredients[]` 每项新增：

```yaml
ingredients:
  - id: cucumber
    name: 黄瓜
    quantity: 300
    unit: g
    role: primary        # primary | supporting | seasoning | garnish | cooking_medium（复用 substitution.schema.json 已有枚举）
    optional: false       # 能否整体省略
    defines_dish: true    # 换掉/去掉后菜品身份是否改变；true 时应通过 variant_of 关系而非 substitutions 处理
```

`role` 复用替换规则 `valid_context.roles` 已有的枚举，不新造词表。`defines_dish` 是本版本新增的判断维度，用来回答"没有黄瓜还叫拍黄瓜吗"这类问题：`defines_dish: true` 的食材一旦被换，产出的应是新菜谱变体（`variant_of` 关系），不是同一道菜的临时调整（`substitutions` 规则）。

**用户体验影响**：这不只是内部数据判断，直接决定 Agent 怎么措辞。缺货食材 `defines_dish: true` 时，回复应该说"这道菜的核心食材缺货，为你找了几个类似的变体/其他菜"，而不是把变体包装成"稍微调整一下同一道菜"——两种说法用户听起来预期完全不同，措辞错了会显得 Agent 在混淆"同一道菜的小调整"和"换了一道菜"，这一点需要在实施阶段写进 Skill 的用户输出契约。

### 2. 替换规则支持真正的通用规则，并分置信度

现有 `valid_context.roles`/`techniques` 字段保留，但需要放开 `packages/recipe-domain/src/replacement.ts` 里"角色/技法规则永远不生效"的保守判断——一旦菜谱有了 `role` 字段，就能实际校验"这道菜里的这个食材是否匹配规则声明的角色"。

为控制误判风险，通用规则（`recipe_ids` 为空、靠 `roles`/`techniques` 匹配）与精确规则（显式列出 `recipe_ids`）需要区分置信度：精确规则可直接作为强候选返回；通用规则标记为较低置信度，在 `find_replacements` 输出中需要显式披露"这是按角色推断的候选，不是针对该菜谱审核过的规则"，不得与精确规则同等呈现。

**产品原则**：新增通用规则的目的是让"能找到候选"的比例上升，但不能以"用户偶尔被一个不靠谱的候选坑一次"为代价——这比"诚实地说没有已审核方案"更伤信任。所以这条不是可选的实现细节，是硬约束：Agent 侧的用户表达也必须原样保留这个置信度区分，不能为了话术流畅把"推断候选"说成"建议"。

### 3. 食材功能分组——评估后决定暂不推进

讨论中曾提出给食材目录加 `functional_groups` 标签（例如"绿叶菜-快炒"），让同组食材互为弱替换候选，避免每两个食材都要手写一条规则。**评估后判断在当前规模下不划算，暂不纳入实施计划**，原因记录如下，供以后重新评估时参考：

- 当前是单人维护的个人知识库（16 道菜），分组体系本身的建立和长期维护成本，很可能超过它能省下的"少写几条替换规则"的收益。
- 分组是比"逐条人工审核规则"更弱的信号，容易产出"能换但味道差很多"这类不容易被发现的错误建议，而这恰恰是最伤用户信任的一类问题（见设计方向 2 的"产品原则"）。
- 替代方案更划算：直接多写几条你认可的、基于 `role` 的通用规则（例如"装饰用的葱姜蒜类基本都能省"），覆盖真实会遇到的场景，不需要额外维护一套分类体系。
- 重新评估的触发条件：如果未来菜谱规模显著增长（比如从 16 道到上百道），手写规则的边际成本变得不可控时，再重新考虑这个方向。

### 4. 菜谱关系补充结构化搭配维度

`recipe-relation.schema.json` 新增可选的 `balance_dimensions`（枚举：`flavor_intensity`/`cooking_method`/`color`/`time`），把"两道菜为什么适合搭配"从自由文本 `reason` 变成可被 Agent 结构化推理的维度，同时给 `variant_of`/`alternative_to` 增加可选的 `distinguishing_ingredient_ids`，说明两道菜的差异具体落在哪些食材上，作为 relations 与食材维度之间的轻量桥接——但不承担完整的食材图职责，那仍然是 substitutions 和 ingredients 角色字段的事。

## 非目标

- 不在本版本实现"食材覆盖率排序"这类新检索能力（第一类场景），留待后续版本单独评审。
- 不要求一次性给全部 16 篇已发布菜谱回填 `role`/`optional`/`defines_dish`；迁移可分批进行，缺失角色字段的菜谱在通用规则匹配时应保守跳过，不得默认赋值。
- 食材功能分组不纳入本版本实施计划（见设计方向 3），不建图数据库/向量检索，延续 V0.3 §14.3 的既有边界。
- 不改变 V0.4 已发布的 8 个 MCP 工具的输入输出契约；`find_replacements` 输出增加置信度披露字段视为向后兼容的扩展，需先过契约测试。
- 不处理同一餐单内多个用餐人偏好不同（例如"大人吃辣、小孩不吃香菜"）这类多主体约束；当前 `exclude_allergens`/`dietary_patterns` 等约束仍是对整个方案生效的单一约束集合，多用餐人场景明确记录为已知缺口，不在本版本方案内。

## 风险

| 风险 | 说明 |
| --- | --- |
| 角色标注质量 | `role`/`defines_dish` 需要人工判断，标错会让通用规则产生错误建议；建议先在少量菜谱试点，观察规则命中效果再扩大范围 |
| 通用规则误判 | 角色匹配无法完全替代人工审核，必须保留置信度分层和披露义务，不能让弱信号冒充强规则 |
| 迁移成本 | 16 篇已发布菜谱的角色回填是人工工作量，不是机械转换；应作为独立、可暂停的维护任务，不阻塞其他功能开发 |

## 验收标准（设计方向 1、2 落地时适用）

1. 给若干试点菜谱回填 `role`/`optional`/`defines_dish` 后，`npm run recipe -- validate` 通过，且这些字段值经过人工审核（不是批量默认赋值）。
2. 用户说"不想吃某道菜里的某装饰性食材"，若该食材在该菜谱里 `role: garnish` 且存在匹配的通用规则，`find_replacements` 必须返回该候选，并明确标注为"按角色推断，未经该菜谱专项审核"。
3. 用户说"某核心食材（`defines_dish: true`）缺货"，`find_replacements` 不得返回同菜谱内的省略/替换候选，只能返回 `variant_of`/`alternative_to` 整菜候选，且 Agent 侧措辞要区分"同一道菜调整"与"换了另一道菜"。
4. 精确规则（`recipe_ids` 命中）与通用规则（角色匹配）在同一次 `find_replacements` 调用的输出中必须可区分置信度，不能合并成一个无差别列表。
5. 缺失 `role`/`optional` 字段的菜谱，通用规则匹配时必须被跳过并可选地给出"该菜谱尚未标注食材角色"的提示，不得静默假设。

## 后续步骤（评审通过后）

1. 先落地"设计方向 1"（角色 + 可选性 + `defines_dish`），这是后续所有能力的地基。
2. 验证少量真实场景后，再决定是否落地"设计方向 2"（通用规则 + 置信度分层）。
3. "设计方向 4"（关系结构化维度）风险和收益相对独立，可延后单独评审。
4. "设计方向 3"（功能分组）不纳入本轮实施计划，仅存档设计思路，重新评估条件见该节。

具体 schema 改动、`replacement.ts` 判断逻辑改动、迁移脚本、Skill 用户表达行为调整与验证计划，将在评审通过后以独立 cowork 记录落地，并同步更新 `specs/knowledge/*.schema.json`、`specs/knowledge/obsidian-knowledge-base-sketch.md`、`specs/behavior/`。
