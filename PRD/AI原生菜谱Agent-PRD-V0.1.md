### 1.1 本版结论

产品从「提供固定页面和多步骤向导的一周食谱 Web 应用」调整为「供 Agent 调用的菜谱领域能力」。

- Agent 负责理解用户、追问必要信息、权衡约束、生成与修改方案。
- Skill 负责告诉 Agent 应如何完成食谱规划任务。
- MCP 服务负责菜谱检索、物价查询、标准化、汇总和校验等工具能力。
- 菜谱知识库由产品维护者自行维护，不开放普通用户或社区直接编辑。
- 首版不开发普通用户 Web 对话产品；可视化网页和分享页属于后续可选客户端。
- 不再把食材周转、采购执行状态机和固定计划步骤作为产品核心。

## 2. 背景与产品判断

旧项目已验证以下事实：

1. 用户对人数、预算、餐次、口味和时间的表达方式非常灵活，固定向导容易显得繁琐。
2. 一周餐单、采购清单、菜谱卡片仍然是有价值的产物。
3. 食材错峰、新鲜度、重复度等因素适合作为内部建议和校验，不适合全部暴露成页面流程。
4. 真正需要长期积累的是高质量菜谱及其结构化信息，而不是越来越复杂的前端状态机。
5. Agent 已经能够承担需求理解、追问、权衡和自然语言修改，产品无需重复实现一套受限的对话逻辑。

因此，新产品的价值不再是「帮用户点完一套计划流程」，而是：

> 为任意兼容客户端中的 Agent 提供可信、可维护的菜谱知识和食谱规划工具，使 Agent 能生成可解释、可修改、可校验的餐单与采购清单。

## 3. 产品目标与非目标

### 3.1 P0 目标

- 提供一份可安装或引用的菜谱规划 Skill。
- 提供一个需要鉴权的远程 MCP 服务。
- 维护者能够以结构化形式新增、更新、发布和归档菜谱。
- Agent 能检索正式菜谱、查询参考物价、汇总采购量并校验候选方案。
- Agent 能通过自然对话完成从需求澄清到生成方案、局部修改的完整流程。
- 输出周期餐单、采购清单、预算估算和菜谱引用等结构化产物。
- 对价格时效、数据来源、AI 草稿和无法满足的约束做明确披露。

### 3.2 P0 非目标

- 不开发面向普通用户的完整聊天网页。
- 不建立用户注册、登录、社交或社区贡献体系。
- 不允许公共调用者修改正式菜谱库。
- 不承诺物价实时、精确或覆盖所有地区和渠道。
- 不做下单、配送、支付或电商导购闭环。
- 不把卡路里或营养信息作为医疗建议。
- 不由 MCP 内部再次调用大模型完成宽泛的「生成方案」。
- 不继续建设独立的食材周转页、采购执行状态机和固定步骤向导。

## 4. 目标用户与核心场景

### 4.1 目标用户

#### A. Agent 使用者

已经在 Codex 或其他兼容 Skill / MCP 的客户端中使用 Agent，希望直接说出需求并获得食谱方案的人。

#### B. 菜谱维护者

产品所有者本人，负责录入、审核、发布和修订菜谱，以及维护食材别名、计量换算和价格数据源。

### 4.2 核心场景

#### 场景 A：生成周期餐单

用户说：

> 我在上海，两个人，下周安排五天晚餐，预算 200 元，不吃香菜，每餐最好 30 分钟内完成。

Agent 提取已有信息，只追问仍会影响方案的缺失项，然后检索菜谱、查询价格、生成方案并校验。

#### 场景 B：局部换菜

用户说：

> 周三换清淡一点，其他天别动。

Agent 只重新检索和修改周三，随后重新汇总受影响的采购项和预算，不整份重做。

#### 场景 C：利用已有食材

用户说：

> 冰箱里还有四个鸡蛋、两个土豆和半颗卷心菜，先消耗这些。

Agent 将已有食材作为偏好或约束，优先检索匹配菜谱，并在采购清单中扣除已有数量。

#### 场景 D：临时处理食材

用户说：

> 买多了一斤鸡胸，今晚可以怎么做？

Agent 检索能够使用鸡胸且符合当前时间、厨具和忌口的菜谱，给出少量候选并解释差异。

#### 场景 E：预算变化

用户说：

> 预算从 200 压到 150，尽量保留周末那两道菜。

Agent 判断哪些约束不可变，替换高成本餐次，再调用价格和校验工具确认结果。

## 5. 总体架构与职责边界

```text
用户
  ↓ 自然语言
Agent + Skill
  ├─ 理解需求与上下文
  ├─ 只追问必要信息
  ├─ 选择并调用 MCP 工具
  ├─ 权衡约束并生成方案
  ├─ 根据用户指令局部修改
  └─ 按产物协议输出结果
  ↓
远程 MCP 服务
  ├─ 菜谱知识库检索
  ├─ 菜谱详情读取
  ├─ 食材名称与单位标准化
  ├─ 物价数据源适配与缓存
  ├─ 采购数量确定性汇总
  └─ 方案规则校验
  ↓
数据层
  ├─ 结构化菜谱及版本
  ├─ 标准食材与别名
  ├─ 单位换算规则
  ├─ 价格记录与来源
  └─ 检索索引
```

### 5.1 Skill 的职责

Skill 是领域工作方法，不保存动态菜谱数据，也不直接连接价格平台。

Skill 应包含：

- 何时触发菜谱规划工作流；
- 如何从自然语言中提取用户已经提供的信息；
- 哪些缺失信息必须追问，哪些可以使用默认值；
- 工具选择、调用顺序和停止条件；
- 硬约束和软偏好的处理方式；
- 失败、无结果、低可信价格等降级策略；
- 周期餐单、采购清单和修改结果的输出契约；
- 不得把知识库外生成内容伪装成已发布菜谱等行为边界。

### 5.2 Agent 的职责

- 理解用户意图和多轮上下文；
- 判断信息是否足够；
- 主动提出最少量的必要问题；
- 从 MCP 返回的菜谱中选择并编排；
- 解释方案为何符合用户约束；
- 生成候选方案并调用 MCP 校验；
- 在用户修改时确定影响范围并局部更新；
- 明确区分事实、估算、建议和 AI 草稿。

### 5.3 MCP 的职责

MCP 提供事实、检索和确定性操作，不替代 Agent 的通用推理。

MCP 不提供宽泛的 `generate_plan(user_message)` 或 `give_solution()`。如果未来出现稳定、可计算的优化需求，可以新增窄而明确的工具，例如 `optimize_meal_sequence`，但仍由 Agent 决定是否采用结果。

### 5.4 可迁移性原则

MCP 协议是主要的跨客户端接口；Skill 的封装可能因 Agent 宿主不同而不同。

新工程应保留一份平台无关的「菜谱规划行为规范」，再分别包装为：

- Codex Skill；
- 其他 Agent 客户端的系统提示或工作流配置；
- 未来 Web 客户端的服务端 Agent instructions。

任何平台适配版不得成为规则的唯一来源。

## 6. Skill 产品规格

### 6.1 建议名称

暂定：`meal-planning`

建议描述：

> 使用已连接的菜谱知识库和价格工具，为用户检索菜谱、规划周期餐单、生成采购清单并按约束修改方案。适用于用户提出做饭安排、菜谱查询、预算规划、剩余食材处理或换菜请求时。

### 6.2 信息收集规则

Agent 必须先从当前消息和历史上下文中提取信息，不得重复询问用户已经回答的内容。

#### 生成周期餐单时通常必须确认

- 时间周期或需要覆盖的日期；
- 用餐人数以及明显不同于普通食量的需求；
- 需要安排的餐次；
- 过敏、忌口和饮食方式；
- 预算是硬上限、目标值还是不限制。

#### 查询物价时必须确认

- 地区，至少精确到城市；
- 用户是否接受参考价格区间；
- 对渠道有明确要求时，需要确认商家或渠道。

#### 仅在会显著影响结果时询问

- 单餐可接受的烹饪时间；
- 厨具和烹饪条件；
- 已有食材及大致数量；
- 辣度、菜系、营养和重复度偏好；
- 是否接受知识库之外的 AI 草稿。

#### 追问原则

- 一次集中询问一至三个最关键问题。
- 可以采用安全、低风险默认值时，先说明假设并继续。
- 过敏原、宗教或严格饮食限制不得自行猜测。
- 用户只查询某道菜时，不启动完整周期规划问卷。

### 6.3 约束等级

#### 硬约束

- 明确过敏原；
- 明确忌口和饮食方式；
- 用户声明的硬预算上限；
- 不具备的关键厨具；
- 指定必须保留或不得修改的餐次；
- 用户明确要求覆盖的日期和餐次。

#### 软偏好

- 菜系和辣度偏好；
- 食材复用和减少浪费；
- 营养多样性；
- 相邻餐次避免高度重复；
- 减少总烹饪时间；
- 优先使用已有食材；
- 参考预算目标。

软偏好发生冲突时，Agent 应说明取舍，不应假装全部满足。

### 6.4 推荐工具调用流程

```text
提取需求
  ↓
判断是否存在阻塞信息
  ├─ 有：进行最少量追问
  └─ 无：继续
  ↓
search_recipes（可按餐次或约束多次检索）
  ↓
get_recipe（读取进入候选方案的完整版本）
  ↓
Agent 生成候选方案
  ↓
aggregate_shopping_list
  ↓
quote_ingredient_prices（用户需要预算时）
  ↓
validate_meal_plan
  ├─ 错误：Agent 修正后再次校验
  ├─ 警告：说明或根据偏好调整
  └─ 通过：输出结构化产物
```

默认最多进行两轮自动修正。仍无法满足硬约束时，停止尝试并告诉用户冲突在哪里、需要放宽什么条件。

### 6.5 修改方案规则

- 优先识别用户要求修改的最小范围。
- 未被用户点名且不受依赖影响的餐次保持不变。
- 换菜后重新计算受影响食材、采购量和预算。
- 若局部修改使硬约束无法满足，应先说明冲突，而不是暗中修改更多餐次。
- 输出本轮发生的变更摘要。

### 6.6 输出产物

#### 周期餐单

- 日期与餐次；
- 菜谱名称、ID 和版本；
- 预计烹饪时间；
- 选择理由或关键匹配项；
- 明确的替代建议；
- AI 草稿标识。

#### 采购清单

- 标准食材名称；
- 汇总需求量和单位；
- 已有数量；
- 建议采购量；
- 关联的日期和菜谱；
- 价格区间、来源、时间和可信度。

#### 方案摘要

- 已满足的硬约束；
- 主要取舍；
- 仍存在的警告；
- 参考预算区间；
- 数据缺口和假设。

## 7. MCP 工具规格

### 7.1 公共只读工具

#### `search_recipes`

用途：根据自然语言和结构化条件检索已发布菜谱。

主要输入：

- `query`：语义查询；
- `meal_types`：早餐、午餐、晚餐或加餐；
- `include_ingredients`；
- `exclude_ingredients`；
- `dietary_constraints`；
- `max_cooking_minutes`；
- `equipment`；
- `difficulty`；
- `limit` 和分页游标。

主要输出：菜谱 ID、当前版本、名称、摘要、匹配原因、核心食材、时间、标签和状态。

规则：默认只返回 `published` 版本；不得用检索摘要代替完整菜谱详情。

#### `get_recipe`

用途：读取指定菜谱的完整结构化内容。

主要输入：`recipe_id`、可选 `version`、需要的份数。

主要输出：菜谱版本、标准食材、按目标份数换算的数量、步骤、厨具、耗时、替代食材、过敏原和来源信息。

规则：未传版本时读取当前已发布版本；返回结果必须标记实际版本。

#### `normalize_ingredients`

用途：将自然语言或多个菜谱中的食材名称、数量和单位转换为可汇总形式。

主要能力：

- 别名映射，如「西红柿」与「番茄」；
- 单位换算，如克、千克、斤；
- 无法精确换算时保留原始值并返回警告；
- 不把不可互换的食材仅因名称相近而合并。

#### `aggregate_shopping_list`

用途：确定性汇总候选餐单需要的食材，并扣除用户已有库存。

主要输入：菜谱 ID 与版本、份数、已有食材。

主要输出：标准食材、总需求、已有量、待采购量、来源菜谱和换算警告。

#### `quote_ingredient_prices`

用途：查询一组标准食材在指定地区和渠道的参考价格。

主要输入：地区、食材、数量、单位、可选渠道和价格时效要求。

主要输出：

- 单价或总价区间；
- 币种；
- 地区和商家；
- 来源链接或数据源标识；
- 查询时间；
- `realtime`、`cached` 或 `benchmark` 数据类型；
- `low`、`medium` 或 `high` 可信度；
- 无法匹配的食材及原因。

规则：不得伪造精确价格；无法查询时返回结构化失败，不使用零元代替。

#### `validate_meal_plan`

用途：校验 Agent 已经生成的候选方案，不负责生成方案。

校验范围：

- 日期和餐次是否完整；
- 菜谱版本是否存在且已发布；
- 忌口和过敏原冲突；
- 硬预算是否超出；
- 厨具和烹饪时间冲突；
- 明显的数量或单位异常；
- 连续高度重复、低多样性等软警告。

输出分为：

- `errors`：必须修正的硬约束冲突；
- `warnings`：允许用户接受的软问题；
- `assumptions`：因信息不足采用的假设；
- `validated_at`：校验时间。

### 7.2 管理能力

P0 不向普通 MCP 调用者暴露管理工具。维护者通过受保护的导入命令或管理接口完成：

- 创建菜谱草稿；
- 更新草稿；
- 校验结构完整性；
- 发布新版本；
- 归档旧菜谱；
- 维护食材别名、单位换算和价格基准。

后续若提供管理 MCP，必须使用单独的服务地址、权限范围或凭证，不能与公共只读凭证共享权限。

## 8. 菜谱知识库设计

### 8.1 菜谱实体 `Recipe`

```text
id
slug
version
status: draft | published | archived
name
summary
meal_types[]
servings
prep_minutes
cook_minutes
difficulty
equipment[]
ingredients[]
steps[]
tags[]
cuisine
dietary_labels[]
allergens[]
substitutions[]
storage_notes
source
created_at
updated_at
published_at
```

### 8.2 菜谱食材 `RecipeIngredient`

```text
ingredient_id
display_name
quantity
unit
preparation
optional
substitution_group
notes
```

禁止只保存「适量」「少许」而没有任何解释。确实无法量化时，应保留原始描述并标记为非精确量，避免采购汇总假装精确。

### 8.3 标准食材 `Ingredient`

```text
id
canonical_name
aliases[]
category
default_purchase_unit
unit_conversions[]
allergen_tags[]
storage_profile
price_query_terms[]
```

### 8.4 版本与发布规则

- 已发布版本不可原地覆盖。
- 修改正式菜谱时创建新版本。
- 检索默认返回当前已发布版本。
- Agent 生成的知识库外菜谱只能保存为 `draft`，且需维护者审核。
- 归档不删除历史版本，已有方案仍能按 ID 和版本解释来源。
- 每次发布需通过食材、步骤、忌口标注和单位完整性校验。

### 8.5 检索策略

首版采用混合检索：

- 结构化过滤处理餐次、时间、厨具、忌口等硬条件；
- 全文或语义检索处理「清淡」「适合夏天」「下饭」等自然语言意图；
- 排序阶段综合匹配度、菜谱完整度和发布时间；
- 不允许语义相似度绕过过敏原、状态等硬过滤。

## 9. 物价能力设计

### 9.1 产品定位

物价是参考信息，不是承诺价格。最终输出应是区间并携带证据，不用虚假的精确总额营造确定感。

### 9.2 数据源策略

价格层采用 `PriceProvider` 适配器：

1. 维护者提供的地区基准价格，作为稳定兜底；
2. 缓存的历史查询结果；
3. 可接入的电商、零售 API 或第三方 MCP / 抓取服务；
4. 未来增加地区或商家适配器时不改变 MCP 工具协议。

### 9.3 价格记录 `PriceQuote`

```text
ingredient_id
query_term
requested_quantity
requested_unit
price_min
price_max
currency
merchant
region
source_type
source_url
queried_at
expires_at
confidence
notes
```

### 9.4 缓存与降级

- 相同地区、食材、渠道和规格在有效期内优先使用缓存。
- 生鲜与常温食品可以设置不同缓存周期。
- 实时查询失败时，按顺序退回缓存和基准价格。
- 降级必须保留数据类型和查询时间，Agent 应在结果中披露。
- 无任何数据时返回未知，不以臆测数值填补。

## 10. 用户流程

### 10.1 首次配置

1. 用户在 Agent 客户端安装或启用 Skill。
2. 用户配置 MCP 服务地址和访问凭证。
3. Agent 确认必需工具可用。
4. 若工具不可用，Skill 应提示配置问题，不进入虚假的完整规划流程。

### 10.2 创建方案

1. 用户自然语言提出需求。
2. Agent 从消息和上下文提取结构化条件。
3. Agent 询问阻塞性的缺失信息。
4. Agent 检索菜谱并读取候选详情。
5. Agent 编排候选餐单。
6. MCP 汇总食材和查询价格。
7. MCP 校验候选方案。
8. Agent 自动修正或向用户解释冲突。
9. Agent 输出餐单、采购清单、预算与假设。

### 10.3 修改方案

1. 用户用自然语言提出局部或全局修改。
2. Agent 识别不可变部分和影响范围。
3. 仅为受影响部分重新检索或编排。
4. 重新汇总和校验。
5. 输出修改后的完整产物和本轮变更摘要。

### 10.4 单次查询

用户只问某道菜、某种食材如何处理或大致价格时，Agent 直接调用相关工具，不强迫用户先创建周期计划。

## 11. 安全、隐私与成本

### 11.1 鉴权

- 远程 MCP 服务默认需要访问凭证。
- 公共只读能力与维护者写入能力分离。
- 凭证不得写入 Skill 文件、菜谱内容或客户端可共享产物。
- 服务端日志不得记录不必要的个人饮食或健康信息。

### 11.2 调用限制

- 按凭证设置每分钟和每日调用额度。
- 物价查询单独限流并优先缓存，因为它可能产生第三方成本。
- 限制单次检索数量、食材数量和自动重试次数。
- 返回结构化的限流与超时错误，便于 Agent 正确解释。

### 11.3 内容安全

- 过敏原属于硬约束，但产品仍需声明不能替代专业医疗建议。
- 菜谱发布前检查生熟食、加热和储存等基础食品安全提示。
- Agent 不得把缺少来源或未审核的内容标记成正式知识库菜谱。

## 12. P0 功能范围

### 12.1 必须实现

- 一个可验证的 Skill 包及平台无关行为规范；
- 远程 MCP 服务与鉴权；
- 结构化菜谱数据和版本状态；
- 维护者导入、校验、发布菜谱的最小流程；
- `search_recipes`；
- `get_recipe`；
- `normalize_ingredients`；
- `aggregate_shopping_list`；
- `quote_ingredient_prices`，至少支持基准价格兜底；
- `validate_meal_plan`；
- 规范化错误响应；
- 基础调用日志、限流和缓存；
- 至少覆盖单次查询、周期规划和局部换菜三类示例。

### 12.2 可以延后

- 菜谱管理 Web 后台；
- 实时电商价格的多渠道覆盖；
- 分享方案的网页渲染器；
- 跨会话保存用户饮食偏好；
- 营养精确计算；
- 社区投稿与审核；
- 自动从图片或网页导入菜谱；
- MCP 内部的复杂排程优化器。

## 13. 验收标准

### 场景 1：信息提取与追问

用户已经提供周期、人数、预算和忌口时，Agent 不重复询问这些字段，只询问查询价格所需的地区等阻塞信息。

### 场景 2：正式菜谱优先

Agent 生成方案中的每道正式菜谱都能追溯到 `recipe_id` 和 `version`。知识库无合适结果时，不伪造引用。

### 场景 3：硬约束校验

候选菜谱包含用户过敏原时，`validate_meal_plan` 返回错误，Agent 不得直接输出为可执行方案。

### 场景 4：参考价格披露

预算结果包含价格区间、地区、来源类型、查询时间和可信度；使用基准数据时明确标识为非实时价格。

### 场景 5：局部修改

用户只要求更换周三晚餐时，其他无依赖餐次保持不变，采购清单和预算只重新计算受影响部分并输出变更摘要。

### 场景 6：工具失败

价格工具超时或限流时，Agent 能使用缓存或基准数据降级；完全无数据时明确说明无法估价，不编造价格。

### 场景 7：无解

预算、忌口、餐次和时间同时导致无解时，Agent 最多自动修正两轮，然后指出冲突并给出最小的放宽建议。

### 场景 8：菜谱版本

已发布菜谱更新后产生新版本，旧版本仍可按 ID 和版本读取，历史方案不会被静默改写。

## 14. 成功指标

首版优先验证工具和知识质量，不以普通消费者注册数为目标。

- 工具调用成功率；
- 菜谱检索后进入最终方案的命中率；
- 硬约束漏检率，目标为零；
- 采购汇总的单位异常率；
- 价格查询命中率与缓存命中率；
- 方案首次生成后无需修改的比例；
- 局部修改时未被要求改变的餐次保留率；
- 单次任务 MCP 调用次数和第三方价格成本；
- 菜谱从草稿到发布的校验通过率。

## 16. 旧项目迁移说明

### 16.1 可复用的产品资产

- 菜谱、标准食材、餐位和警告等部分数据模型经验；

### 16.2 不直接迁移的实现

- 固定多步骤计划向导；
- 同时存在的进度条和结果 Tab；
- Hash 路由下的页面状态机；
- 采购执行状态和食材周转页面；
- 把所有规则固化在前端的计划生成器；
- 为普通访客设计的公开 AI Key 消耗模式。

### 16.3 历史版本处置

- 旧 Web MVP 保留为规则型产品验证和设计过程记录。
- 当前未发布的新版本不因本 PRD 自动部署。
- 新方向在新工程实施，不在旧工程直接重构，避免混合两套产品目标。

## 17. 风险与待验证问题

### 17.1 主要风险

- 不同 Agent 客户端对 Skill、MCP、结构化输出和多轮状态的支持不同。
- 菜谱数据不足时，Agent 可能频繁返回相似方案或转向 AI 草稿。
- 食材单位不规范会直接污染采购汇总和预算。
- 中国本地生鲜价格缺少统一、稳定且低成本的数据源。
- Agent 过度追问会让对话重新变成向导，追问不足又会产生大量假设。
- MCP 同时暴露读写能力会增加菜谱库被误改的风险。

### 17.2 实施前需要决定

1. 首个明确支持的 Agent 客户端及 Skill 格式。
2. MCP 使用个人访问令牌、OAuth 还是其他鉴权方式。
3. P0 菜谱内容采用 JSON、YAML、Markdown 加 frontmatter，还是直接使用数据库。
4. 初始准备多少份菜谱，才能覆盖有意义的检索和一周规划。
5. 首个价格地区和基准价格维护方式。
6. Agent 生成 AI 草稿菜谱是否仅展示，还是允许提交到维护者待审核队列。
7. 产物是否需要机器可读 JSON 与用户可读 Markdown 双格式。

## 18. 推荐实施顺序

1. 定义菜谱、食材、价格和产物的数据契约。
2. 准备一小批高质量、覆盖不同餐次和约束的种子菜谱。
3. 实现菜谱检索与详情读取工具。
4. 实现食材标准化、采购汇总和方案校验。
5. 加入基准价格与统一价格适配器。
6. 编写 Skill 和平台无关行为规范。
7. 使用真实对话场景做端到端测试，重点观察追问和局部修改。
8. 再决定是否接入实时价格源、管理后台和分享网页。
