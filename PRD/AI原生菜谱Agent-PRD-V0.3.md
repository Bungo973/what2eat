### 1.1 相对 V0.2 的主要变化

- 新增可下载、可打印、自包含的 HTML 餐单产物，同时保留 Markdown 降级输出。
- 引入统一的 `MealPlanArtifact` 结构化产物，餐单、菜谱、采购、价格和 HTML 均从同一份数据生成。
- 价格能力改为显式三态：不报价、参考报价、硬预算；用户未提出价格或预算时不调用价格工具。
- Markdown 知识库从“独立菜谱文档集合”演进为“菜谱、食材、技法、替换规则和菜谱关系组成的轻量知识图谱”。
- Obsidian 作为维护和浏览界面，但不成为 MCP 运行时依赖；Markdown 和 schema 仍是事实与质量边界。
- 将“超预算换菜”和“食材缺货替换”定义为正式产品场景，所有替换必须重新汇总、报价（如需）并校验。
- 增加关系索引与混合检索方向；V0.3 试点仍不要求图数据库或向量数据库。

## 2. 背景与问题

V0.2 已能提供可追溯菜谱、周期餐单、采购汇总、硬约束校验和参考价格，但用户体验与知识表达存在三个限制：

1. 长餐单主要依赖 Markdown 长文，菜单、做法、采购和预算之间不够直观。
2. 菜谱之间缺少可机器读取的关系；正文中的“替换建议”无法可靠支持自动换菜。
3. 当前检索主要依赖名称、标签、摘要和食材命中，难以回答“同样适合晚餐但更便宜”“这个食材买不到时怎么调整”等关系型问题。

V0.3 的目标不是增加更多自由生成，而是让已有事实更容易看懂、关联、检索和重算。

## 3. 产品目标与非目标

### 3.1 目标

- 用户能收到层次清楚的餐单 HTML：先看菜单，再看菜谱、采购、可选预算和警告。
- HTML、Markdown 和工具校验使用同一份结构化数据，不出现数量或结论漂移。
- 预算是条件能力：未请求时不询问地区、不报价、不显示预算区块。
- 维护者能在 Obsidian 中浏览菜谱关系、食材别名、替换规则和技法关联。
- Agent 能基于已发布关系处理超预算、食材缺货和局部换菜，并展示修改前后差异。
- 运行时价格只用于排序和重算，不写回静态菜谱知识。
- 所有进入正式方案的菜谱、变体和替换规则均可追溯到稳定 ID、版本和发布状态。

### 3.2 非目标

- 不在 V0.3 建设消费者账号、社区、支付、下单或配送系统。
- 不把 Obsidian 社区插件设为服务端必需依赖。
- 不要求一次性建设完整食品本体、营养医学系统或自动生成所有替换关系。
- 不允许 Agent 根据相似名称自行发布食材替换规则。
- 不把 HTML 作为新的事实源，也不从 HTML 反向恢复餐单数据。
- 不承诺参考批发价或跨地区基准能验证零售硬预算。
- 不在 MCP 中加入宽泛的自然语言餐单生成工具。

## 4. 用户与核心场景

### 4.1 餐单规划与 HTML 查看

用户给出日期、餐次、份数和必要约束后，Agent 返回简短文字结论，并提供结构清晰的 HTML 产物。HTML 至少包含：

1. 计划摘要；
2. 日期与餐次菜单；
3. 菜谱卡和完整做法；
4. 采购清单；
5. 条件性价格与预算；
6. 备选项、假设和警告。

### 4.2 超预算后的动态调整

用户认为方案太贵，或明确要求降低目标金额时：

1. 使用报价结果识别价格贡献较高或价格未知的采购项；
2. 优先查找已发布菜谱变体和已审核替换规则；
3. 局部食材替换不可靠时，替换整道菜；
4. 重新读取菜谱、汇总采购、报价并校验；
5. 输出原方案与新方案的菜谱、采购和价格差异。

静态知识只说明“可否替换以及怎样改做法”，动态价格决定“这次是否更便宜”。

### 4.3 食材缺货

用户说明某种食材买不到时：

1. 先通过别名目录解析为标准食材 ID；
2. 判断食材是核心、辅助、调味、装饰还是烹饪介质；
3. 优先选择当前菜谱已审核的省略或替换规则；
4. 没有可靠局部替换时，查找不含该食材的同餐次替代菜谱；
5. 重新汇总和校验完整方案。

### 4.4 知识库维护

维护者通过 Obsidian 模板创建或编辑草稿，使用链接查看关联实体，通过 CLI/schema 校验后发布。Obsidian 的图谱和 Bases 用于理解和维护，不替代发布校验。

## 5. 产品原则

1. **单一结构化产物**：先形成可校验数据，再渲染 Markdown 或 HTML。
2. **关系必须有语义**：不保存模糊的“相关”，而保存 `variant_of`、`alternative_to`、`pairs_with` 等明确关系。
3. **替换依赖上下文**：食材相似不等于在任意菜谱中可互换。
4. **静态知识与动态事实分离**：菜谱库保存能力、关系和做法；价格 provider 保存当次市场事实。
5. **人工事实与派生索引分离**：人工维护审核过的关系；共享食材比例、价格排序等运行时计算。
6. **渐进迁移**：先用少量菜谱验证 schema，不要求一次性重写全部知识库。

## 6. 总体架构

```text
用户自然语言
    ↓
Agent + Skill
    ├─ 提取约束与预算模式
    ├─ 编排菜谱和替换候选
    └─ 选择 Markdown 或 HTML 交付
    ↓
MCP 领域能力
    ├─ 菜谱与关系检索
    ├─ 读取菜谱和替换规则
    ├─ 采购汇总
    ├─ 条件性报价
    ├─ 方案校验
    └─ 确定性 HTML 渲染
    ↓
MealPlanArtifact
    ├─ Markdown 摘要
    └─ 自包含 HTML
    ↓
Markdown/Obsidian 知识库
    ├─ 菜谱版本
    ├─ 标准食材
    ├─ 替换规则
    ├─ 技法与厨具
    └─ 菜谱关系
```

运行时索引、HTML、缓存和报价均为派生产物；删除后可从知识库和当次工具结果重新生成。

## 7. 需求与预算模式

内部需求对象增加显式模式：

```yaml
pricing:
  mode: off # off | reference | hard
  region: null
  merchant: null
budget:
  amount: null
  currency: CNY
```

| 模式 | 触发条件 | 地区是否阻塞 | 是否报价 | 是否做硬预算判断 |
| --- | --- | --- | --- | --- |
| `off` | 用户没有提价格、便宜或预算 | 否 | 否 | 否 |
| `reference` | 用户问价格、花费、便宜方案或希望降低成本 | 是 | 是 | 否 |
| `hard` | 用户明确给出不可超过的金额 | 是 | 是 | 仅在 `budget_status=verified` 时 |

如果用户只说“预算 100 元”而未说明硬上限或参考目标，Agent 应集中追问一次，不默认升级为硬约束。

## 8. `MealPlanArtifact` 与 HTML 产物

### 8.1 结构化产物

V0.3 应定义版本化 schema，至少包含：

```text
artifact_version
plan_id
generated_at
locale
scope                 日期、餐次、份数
constraints           已确认约束与假设
meals[]               日期、餐次、recipe_id、version
recipes[]             目标份数食材与步骤
shopping              汇总采购和警告
pricing|null          报价、覆盖、预算状态
validation            errors、warnings、assumptions
alternatives[]        可选替换及差异
```

`pricing` 在 `pricing.mode=off` 时必须为 `null` 或缺省，不能为了填满页面调用价格工具。

### 8.2 HTML 信息结构

HTML 固定采用以下信息顺序：

1. 顶部计划摘要和约束标签；
2. 日期 × 餐次菜单表；
3. 可折叠菜谱卡；
4. 分类采购表；
5. 条件性预算摘要表和逐项价格表；
6. 替换方案与变化表；
7. 假设、警告、价格来源和版本信息。

### 8.3 渲染要求

- 输出为自包含 UTF-8 HTML；首版不依赖外部 JavaScript、字体或图片 CDN。
- 使用语义化标题、表格、列表和 `<details>`；支持键盘、窄屏和浏览器打印。
- 不在模板内执行份数缩放、采购汇总、价格换算或硬约束判断。
- 所有数量、价格和警告来自 `MealPlanArtifact`。
- 对宿主无法展示文件的情况，始终保留完整 Markdown 降级输出。
- HTML 文件名不包含用户隐私或未经清理的自然语言。

### 8.4 HTML 交付边界

原始 HTML 直接写进聊天可能被宿主转义或清理。推荐由确定性 renderer 生成文件或 MCP 资源，再由 Agent提供摘要和资源链接。是否发布为新增公共工具，应在实现前通过工具契约评审；候选能力名为 `render_meal_plan_html`。

## 9. 知识库 V0.3 模型

### 9.1 实体

| 实体 | 稳定标识 | 主要事实 |
| --- | --- | --- |
| 菜谱版本 | `recipe_id + version` | 份数、食材、步骤、时间、约束、关系 |
| 标准食材 | `ingredient_id` | 名称、别名、分类、过敏原、单位、价格源映射 |
| 替换规则 | `substitution_id + version` | 原食材、替代食材、比例、上下文、步骤变化、风险 |
| 技法 | `technique_id` | 输入状态、厨具、时间、适用食材角色和失败点 |
| 厨具 | `equipment_id` | 名称、别名、能力和可替代厨具 |
| 菜谱关系 | 关系记录或菜谱内关系 ID | 变体、同餐次替代、搭配、剩余食材利用 |

V0.3 试点不要求把“餐单”写回知识库；用户餐单是运行时产物，不是公开菜谱事实。

### 9.2 关系类型

首批只支持有明确产品用途的关系：

| 关系 | 含义 | 主要用途 |
| --- | --- | --- |
| `variant_of` | 同一道菜的正式风格或配方变体 | 保留菜品身份的换法 |
| `alternative_to` | 可占用相同餐次角色的另一菜谱 | 缺货、超预算时整菜替换 |
| `pairs_with` | 经审核适合一起组成一餐 | 组合菜单 |
| `uses_leftover_from` | 可消耗另一菜谱的剩余产物 | 剩余食材规划 |
| `substitutes_for` | 有上下文的食材替换 | 局部改菜 |
| `requires_technique` | 菜谱或替换需要特定技法 | 可执行性校验 |

“共享食材”“文本相似”“这次更便宜”由运行时索引计算，不人工保存成永久关系。

### 9.3 食材在菜谱中的角色

每条菜谱食材增加：

```yaml
role: primary # primary | supporting | seasoning | garnish | cooking_medium
optional: false
step_refs: []
substitution_rule_ids: []
```

角色用于决定缺货时的处理方式：装饰食材可能允许省略，核心食材通常需要正式变体或整菜替换。

### 9.4 替换规则

替换规则不能只写一句自然语言，至少包含：

```yaml
schema_version: 1
substitution_id: scallion-omit-as-garnish
version: 1
status: draft
from_ingredient: scallion
to_ingredient: null
mode: omit
valid_context:
  roles: [garnish]
  techniques: []
  recipe_ids: []
ratio: null
step_changes:
  - 删除最后撒葱花的步骤
allergen_changes:
  add: []
  remove: []
effects:
  flavor: 葱香减少
  texture: 无显著变化
  time_delta_minutes: 0
evidence:
  type: maintainer_review
  source: null
reviewed_at: null
```

只有 `published` 规则可被 Agent 自动采用。草稿规则只能供维护者审阅。

### 9.5 Obsidian 兼容策略

- 文件名便于阅读，稳定 ID 仍由 frontmatter 决定，不能用文件名代替 ID。
- 可查询字段尽量保持为文本、数字、日期、标签和链接列表。
- 复杂食材数量和替换上下文继续由 schema 管理；不因 Obsidian 属性面板不支持嵌套而降级为自由文本。
- 为 Obsidian 图谱生成扁平链接字段或“关联”章节，但详细食材列表仍只有一个权威来源。
- `.base` 文件只定义视图和筛选，不保存知识事实。
- 修改已发布菜谱仍必须创建更高版本，不能因 Obsidian 编辑方便而原地覆盖。

## 10. 检索与命中

V0.3 使用分层检索，不让语义相似覆盖硬约束：

1. 别名解析为标准食材、技法和厨具 ID；
2. 发布状态、过敏、忌口、餐次、厨具和时间硬过滤；
3. 菜谱关系和替换规则扩展；
4. 名称、标签、摘要和正文全文检索；
5. 按库存复用、当前价格、缺货条件和用户软偏好重新排序；
6. 数据量足够且有评测集后，再考虑向量召回或语义重排。

搜索结果必须说明命中来自精确字段、别名、关系还是全文；动态价格排序必须附报价范围和实际地区。

## 11. 自适应换菜流程

### 11.1 候选优先级

1. 当前菜谱已发布的省略规则；
2. 当前菜谱已发布的食材替换规则；
3. 同一菜谱的已发布变体；
4. 关系明确的整菜替代；
5. 经过硬过滤的普通搜索候选；
6. 用户明确接受时的 AI 草稿。

### 11.2 重新计算不变量

任何改变只要影响正式餐单，就必须：

- 读取新菜谱或替换规则的确切版本；
- 重新生成目标份数食材；
- 重新汇总完整采购；
- 原请求包含价格时重新报价；
- 重新校验完整餐单；
- 返回变化表和新增风险。

知识库中的 `alternative_to` 不得静态写“更便宜”；是否便宜必须以当次地区报价重算。

## 12. MCP 与工具演进

现有六个公共工具保持向后兼容。V0.3 先通过现有工具和扩展字段验证知识模型，再评审以下候选窄工具：

### 12.1 `find_replacements`（候选）

输入包括当前 `recipe_id/version`、问题类型、不可用食材、硬约束和可选报价上下文。输出只返回已发布的替换规则、变体和整菜备选，不生成最终方案。

### 12.2 `render_meal_plan_html`（候选）

输入为通过 schema 校验的 `MealPlanArtifact`，输出 HTML 内容或 MCP 资源引用。它不搜索、不报价、不修改方案。

任何新增公共工具都必须先定义共享 schema、契约测试、错误契约和兼容策略。

## 13. 内容质量与发布

### 13.1 菜谱发布底线

- 每个食材能解析为标准 ID，或明确标记 unresolved；
- 每个可量化食材有数值和受控单位；
- 核心食材标注角色和可选性；
- 步骤完整，包含关键时间、火候和熟度判断；
- 过敏原由食材目录复核；
- 关系目标和替换规则存在且版本状态合法；
- 来源、授权和维护者审核信息可追溯；
- 已发布版本不可原地修改。

### 13.2 替换规则发布底线

- 说明适用角色、技法或菜谱范围；
- 提供比例或明确说明无法按比例替换；
- 说明步骤、时间、口感和过敏原变化；
- 规则经过人工审核；
- 不以价格高低作为永久事实；
- 无法确认安全性或成型影响时不得发布为自动规则。

## 15. 验收标准

### 场景 1：无预算餐单

用户只要求两天晚餐时，不追问地区、不调用报价工具；HTML 不出现空预算表。

### 场景 2：参考价格

用户询问大概花费时，HTML 展示预算摘要和逐项价格表，明确本地、省级、全国及跨地区参考的区别。

### 场景 3：HTML 一致性

HTML 和 Markdown 中的菜谱版本、目标份数、采购量、总价区间和校验结论与同一 `MealPlanArtifact` 完全一致。

### 场景 4：窄屏与打印

HTML 在 320px 宽度下无内容遮挡；打印时菜单、采购和价格表可读，交互控件不成为必要信息入口。

### 场景 5：超预算调整

用户要求降低花费时，系统基于当次价格选择已发布备选，重新计算完整采购和价格，并展示变化；未验证价格不得声称满足硬预算。

### 场景 6：食材缺货

核心食材缺货且无已发布替换规则时，系统不自行编造比例，而返回整菜备选或请求用户接受草稿。

### 场景 7：Obsidian 维护

维护者能通过链接从菜谱跳转到食材和替换规则，通过 Bases 查看“缺少替换规则”“未发布”“含特定食材”等列表。

### 场景 8：版本与关系完整性

删除或归档关系目标时，知识库校验能报告悬空引用；历史菜谱版本仍可读取。

## 16. 成功指标

- HTML 生成成功率和 schema 一致性错误数；
- 用户展开菜谱、打印或保存 HTML 的可用性反馈；
- 无预算请求中的误报价率，目标为零；
- 标准食材和别名解析覆盖率；
- 已发布菜谱的食材角色完整率；
- 替换规则审核通过率和实际采用后的二次修改率；
- 超预算场景中成功给出可验证降价方案的比例；
- 缺货场景中无需 AI 草稿即可解决的比例；
- 悬空关系、非法版本和过敏原漏检率，目标为零。

## 17. 风险与待评审决定

| 风险或决定 | 当前建议 |
| --- | --- |
| 宿主是否渲染原始 HTML | 不依赖宿主；生成独立 HTML 资源并保留 Markdown |
| Obsidian 不支持复杂嵌套属性编辑 | 简单关系用链接属性，复杂事实继续受 schema 管理 |
| 人工关系维护成本过高 | 只维护有产品语义的关系，其余关系运行时派生 |
| 替换规则看似正确但破坏菜品 | 必须标注上下文、步骤变化和发布审核 |
| 动态价格污染静态知识 | 价格不写回菜谱；每次换菜重新报价 |
| 新工具导致公共契约膨胀 | 先用 schema 试点，确认必要后再做加法发布 |
| 外部菜谱版权和来源不清 | 只保存获授权、自有或允许使用的内容，并保留来源证据 |

## 18. 结论

V0.3 延续“轻量 Skill + 确定性 MCP + Markdown 事实源”的边界，但将最终结果统一为可验证的 `MealPlanArtifact`，并增加 HTML 展示层和关系型知识模型。

Obsidian 负责让维护者看见和编辑知识关系；schema、版本校验和发布流程负责保证机器可用性。菜谱是否能替换由知识库决定，这次是否值得替换由库存、地区价格和用户约束决定。
